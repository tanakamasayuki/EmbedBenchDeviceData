# Unit Glass (U158) — 透過 OLED 表示ユニット

> 128×64 の透過 OLED に、図形と文字を「描画コマンド」として I2C で送るユニット。
> ホストはピクセルバッファを持たず、描く内容だけを指示する。ボタン 2 個とブザーも同じ
> レジスタ空間に載っている。
>
> **確度**: [`profiles/m5stack-mcu-u158.yaml`](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/profiles/m5stack-mcu-u158.yaml) の
> レジスタマップは `M5Unit-GLASS` ライブラリのソースから起こした推定
> （`evidence.source: inferred` / `confidence: tentative`）で、**実測では未確認**。
> 本文はベンダーの Unit Glass I2C Protocol PDF（firmware V4、2023-03-08）とも突き合わせてあり、
> 引数の意味・値域・バッファ上限は PDF 由来である。実機のキャプチャはまだ無い。

## これは何か

1.51 インチの透過 OLED パネル（SSD1309 駆動、128×64、青単色、1bit）と、ボタン 2 個、ブザーを、
STM32F030F4P6 に載せた M5Stack ファームウェアが束ねているユニット。

**重要な性質として、これは SSD1309 を直接叩くディスプレイではない。** SSD1309 はユニット内部で
MCU に繋がっていて、外部 I2C バスには出ていない。ホストが送るのは SSD1309 のコマンド/データ
ストリームではなく、「(x, y) に円を描け」「バッファを表示しろ」といった**描画コマンド**である。
そのため転送は毎回「ポインタバイト + 固定長ペイロード」という普通のレジスタ書き込みの形をしており、
本リポジトリでも `i2c-register` として記録している。

（型番の似た Unit Glass2（U158-B）は中身が違い、そちらは SSD1309 が直接バスに出ている。
本ガイドは U158 のみを扱う。）

できること:

- 点・線・円・文字列・ビットマップを描ける。描画モードは 1 = 塗る、0 = 消す。
- オフスクリーンのフレームバッファに描いてから、まとめて表示に反映できる。
- 表示の向き（0°/180°）と白黒反転を切り替えられる。
- パネルの ON / OFF を切り替えられる。
- ボタン A / B の状態を読める。
- ブザーを鳴らせる（周波数とデューティを指定）。

できないこと・持っていないもの:

- **割り込み線は無い。ボタンの変化を知るにはポーリングするしかない。**
- **画面の内容を読み返せない。** 描画系は全部書き込み専用で、フレームバッファを読むレジスタが無い。
  「いま何が表示されているか」はホスト側で覚えておくしかない。
- **I2C アドレスを変更する手段が無い。** アドレスレジスタが PDF にもライブラリにも存在しない。
  同じバスに 2 台並べることはできない。
- **文字列バッファは 64 バイト、画像バッファは 1024 バイトが上限**（PDF）。1024 バイトは
  128×64 の 1bit 画面ちょうど 1 枚分である。
- フォントは firmware 内蔵の 2 種（サイズ 8 と 16）だけ。任意フォントは画像として送るしかない。
- 描画の完了通知が無い。ライブラリは代わりに固定の待ち時間を入れている（下記）。

## レジスタ（描画コマンド）

| アドレス | 長さ | R/W | 意味 |
|---|---|---|---|
| `0x00` | 1 | W | フレームバッファのクリア。`1` を書く |
| `0x10` | 1 | W | フレームバッファをパネルに反映。`1` を書く。**これを書くまで何も表示されない** |
| `0x20` | 4 | W | 文字列の描画: x, y, フォントサイズ, モード。**サイズは 8 か 16**。描く内容は事前に `0x80` に入れておく |
| `0x30` | 3 | W | 点: x, y, モード |
| `0x40` | 5 | W | 線: x1, y1, x2, y2, モード |
| `0x50` | 4 | W | 円: x, y, 半径, モード |
| `0x60` | 1 | W | 表示の向き。`0` 正置き / `1` 正置き 180° 回転 / `2` 反転表示 / `3` 反転表示 180° 回転 |
| `0x70` | 1 | W | パネルの ON(`1`) / OFF(`0`) |
| `0x80` | 3 | W | 文字列バッファに 1 文字格納: index 下位, index 上位, 文字。**1 文字につき 1 転送**。上限 64 バイト |
| `0x90` | 3 | W | 画像バッファに 1 バイト格納: index 下位, index 上位, データ。**1 バイトにつき 1 転送**。上限 1024 バイト |
| `0xA0` | 1 | W | 白黒反転。`0` 通常 / `1` 反転 |
| `0xB0` | 5 | W | ビットマップの描画: x, y, 幅, 高さ, モード。描く内容は事前に `0x90` に入れておく |
| `0xC0` | 3 | W | ブザーの音: 周波数 16bit **LSB first（単位 Hz）**、続けてデューティ 1 バイト |
| `0xC3` | 1 | W | ブザーの起動(`1`) / 停止(`0`) |
| `0xD0` | 1 | R | ボタン A。**押下で `0`（アクティブ Low）** |
| `0xD1` | 1 | R | ボタン B。**押下で `0`（アクティブ Low）** |
| `0xFE` | 1 | R | ファームウェアのバージョン |

- **モード**引数は共通で `1` = 塗る、`0` = 消す（PDF の注記）。
- デューティは 0〜255 で指定する。PDF の例では 50% = `255 * 0.5 = 127`。
- `0xC0`〜`0xC3` は本来 1 つの 4 バイトブロック（周波数下位, 周波数上位, デューティ, 起動）で、
  `0xD0`〜`0xD1` は 1 つの 2 バイトブロックである。ライブラリはこれを上表のサブレジスタとしてしか
  触らない。`0xC3` と `0xD1` はヘッダの `#define` に無く、メソッド本体で
  `GLASS_DRAW_BUZZ_REG + 3` / `GLASS_DRAW_KEY_REG + 1` として組み立てられている。

**転送の形**: 書き込みは「ポインタバイト + 固定長ペイロード」を 1 トランザクションで送る。
読み出しはポインタバイトを書いて **repeated START**（`endTransmission(false)`）を打ち、続けて
必要な長さを要求する。ただし `getFirmwareVersion()` だけは repeated START ではなく STOP を挟み、
しかも読み出しに `_wire` ではなくグローバルの `Wire` を使う（後述）。

## 典型的な使い方

1. `0xFE` を読んでファームウェアのバージョンを確認する（通信確認も兼ねる）。
2. `0x60` に向き、`0xA0` に白黒反転を書いて表示の基本設定をする。
3. `0x00` に `1` を書いてフレームバッファを消す。
4. 文字を出すなら、**まず** `0x80` に 1 文字ずつ（index 0 から順に）書き込み、**そのあと**
   `0x20` に `{x, y, サイズ, モード}` を書く。
5. 図形を出すなら `0x30` / `0x40` / `0x50` を書く。
6. ビットマップを出すなら、**まず** `0x90` に 1 バイトずつ書き込み、**そのあと**
   `0xB0` に `{x, y, 幅, 高さ, モード}` を書く。
7. **`0x10` に `1` を書く。ここで初めて画面が変わる。**
8. ボタンは `0xD0` / `0xD1` を周期的に読む。`0` が押下。
9. 鳴らすなら `0xC0` に `{周波数下位, 周波数上位, デューティ}`、続けて `0xC3` に `1`。
   止めるときは `0xC3` に `0`。

## 利用上の注意

- **`0x10`（Show）を書かないと何も表示されない。** 描画レジスタはすべてオフスクリーンの
  フレームバッファに対する操作である。「コマンドは通っているのに画面が変わらない」の原因は
  たいていこれ。
- **文字列・ビットマップは「バッファに入れてから描く」の 2 段階。** `0x20` と `0xB0` は
  *引数を受け取らない*。描く内容は直前に `0x80` / `0x90` に入っているものになる。順番を逆にすると
  前回の内容が描かれる。
- **文字列に終端が書かれない。** ライブラリの `set_string_buffer()` は index 0 から 1 文字ずつ
  書き込むだけで、ヌル終端も長さも送らない。そのため**前回より短い文字列を書くと、前回の
  末尾が残る**。ベンダーのサンプルが `"Count: " + count + "      "` と末尾に空白を足しているのは
  この後始末である。
- **1 文字 / 1 バイトにつき 1 トランザクション。** ビットマップ 1 枚（128×64 = 1024 バイト）を
  送ると、**1024 回の I2C 書き込み**になる。100kHz では 1 枚に数百 ms かかる計算で、
  アニメーションには向かない。文字列バッファも同じ方式（上限 64 バイト）。
- **ボタンはアクティブ Low。** `0xD0` / `0xD1` の値をそのまま「押されている」と解釈すると
  意味が逆になる。ベンダーのサンプルも `getKeyA() == 0` を押下として扱っている。
- **firmware がビジーになる区間がある。** ライブラリは文字列描画・向き変更・白黒反転のあとに
  1 ms、**パネル ON/OFF のあとに 1 秒**の待ちを入れている。とくに `0x70` のあとの 1 秒は
  ホスト側を丸ごとブロックするので、ループの中で気軽に呼ぶレジスタではない。この区間に
  次のトランザクションを出すと NAK される可能性がある（PDF も文字列描画について
  「need 1 ms delay after draw string」と書いている）。
- **`0x60` は真偽値ではない。** 0〜3 の 4 値で、向きの反転と表示の反転が同居している。
  boolean のつもりで `1` を書くと画面が 180° 回る。色を反転したいなら `0xA0` の方。
- **線の端点はライブラリ側で入れ替えられる。** `draw_line()` は `y2 < y1` のとき端点を
  交換して送る。バスに出るバイト列は必ず「y の小さい方が先」になるので、キャプチャを
  引数と突き合わせるときに食い違って見える。デバイスの仕様ではなくライブラリの都合。
- **アドレスが変えられないので、同じバスに 2 台は並べられない。** 2 枚使うなら I2C マルチプレクサ
  （PaHub など）が要る。
- **`getFirmwareVersion()` だけ転送の形と使うバスが違う。** repeated START ではなく STOP を挟み、
  さらに読み出しを `Wire.read()`（グローバル）で行っている。`begin()` に `Wire1` を渡した構成では、
  この 1 メソッドだけ別のバスから読もうとして壊れる。
- **画面の内容を読み返せない。** 表示状態はホスト側で管理する前提。再描画のたびに
  `0x00` → 描画 → `0x10` を通すのが安全。

## 出典と確度

- レジスタのアドレスと転送長: `M5Unit-GLASS` ライブラリのソース
  （`collection/vendor/M5Unit-GLASS` に commit 固定で取得）。`0xC3` と `0xD1` はヘッダには無く、
  メソッド本体の `+3` / `+1` から起こした。
- 引数の意味、モード（1 = 塗る / 0 = 消す）、`0x60` の 4 値、フォントサイズ 8 / 16、
  ブザー周波数の単位 Hz、デューティの与え方、バッファ上限（文字列 64 / 画像 1024）:
  ベンダーの Unit Glass I2C Protocol PDF（V4、2023-03-08）。**ライブラリのソースにはこれらの
  記述が無い。**
- 待ち時間（描画後 1 ms、パネル ON/OFF 後 1 秒）: ライブラリの実装から。firmware 側の
  実際のビジー時間は**未確認**。
- ボタンのアクティブ Low: PDF は「0 or 1」としか書いていない。押下 = `0` はベンダーの
  サンプルコードの扱いから起こした**推定**。
- **PDF 側の誤り**: PDF はファームウェアバージョンを `0xF0` と書いているが、ライブラリは
  `0xFE` を読む。M5Stack の他ユニットの protocol PDF にも同じ誤植があるため、`0xFE` を採った。
- **未確認**: 実機のキャプチャがまだ無い。給電が 5V か 3.3V か、`0x20` などの書き込み中に
  NAK が出るのか、400kHz で動くかは確かめられていない。
- **未調査**: このユニットはボタンとバージョン以外すべて書き込みであり、probe が read-only の
  ため描画系には一切触れていない。読めるのは `0xD0` / `0xD1` / `0xFE` だけである。
