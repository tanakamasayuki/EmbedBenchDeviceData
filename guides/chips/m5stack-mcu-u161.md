# Unit ExtEncoder (U161) — 外付けインクリメンタルエンコーダ入力ユニット

> 外部の A/B（+ Z）出力エンコーダを繋ぐと、パルスの計数と、それを距離[mm]に換算した値を
> I2C から読めるユニット。計数と換算はユニット上の STM32F030 のファームウェアが行う。
>
> **確度**: [`profiles/m5stack-mcu-u161.yaml`](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/profiles/m5stack-mcu-u161.yaml) の
> レジスタマップは `M5Unit-ExtEncoder` ライブラリのソースから起こした推定
> （`evidence.source: inferred` / `confidence: tentative`）で、**実測では未確認**。
> 本文はベンダーの Unit ExtEncoder I2C Protocol PDF とも突き合わせてあり、単位・Z モードの
> 意味・ASCII の桁構成は PDF 由来である。実機のキャプチャはまだ無い。

## これは何か

ホスト側の GPIO とタイマを消費せずに、外付けのインクリメンタルロータリエンコーダを数えるための
ユニット。エンコーダは Grove ではなく **VH2.54-5P のコネクタ**に繋ぐ。A/B の 2 相、または
Z（インデックス、1 回転に 1 パルス）を加えた 3 相に対応する。

計数を担当するのは STM32F030F4P6 に載った M5Stack ファームウェアで、ホストから見えるのは
その STM32 である。**つまり I2C の相手は固定機能 IC ではなくファームウェアであり、
レジスタマップはこの製品固有のもの**である。

用途は、車輪の走行距離の計測、送り機構の位置検出、手回しダイヤルの読み取りなど。
「1 回転あたりのパルス数」と「1 回転あたりの進む距離（円周）」をユニットに教えておくと、
firmware がパルス数を距離[mm]に直して返してくれる。

できること:

- パルスの累計（エンコーダ値）を 32bit で読める。
- 距離を **mm 単位の整数**で読める。
- 同じ距離を **m 単位の ASCII 文字列**（符号 + 4 桁 + 小数 3 桁）でも読める。
- Z パルスが来た回数、すなわち回転数を読める。この値は書き込んで任意の値に設定もできる。
- 車輪の円周[mm]と 1 回転あたりのパルス数を設定でき、読み返せる。
- Z パルスでカウントを自動クリアするかどうかを選べる。
- カウントを 0 に戻せる。
- I2C アドレスを変更できる。

できないこと・持っていないもの:

- **割り込み線は無い。変化を知るにはポーリングするしかない。**
- **回転方向・回転速度を直接は返さない。** 返るのは累計値だけ。速度が要るならホスト側で
  時間差から求める。
- **A / B / Z の生の信号レベルを読めない。** 配線が正しいかを firmware 経由で確かめる術が無い。
- **逓倍（x1 / x2 / x4）の設定も、現在どの逓倍で数えているかの読み出しも無い。**
  「1 回転あたりのパルス数」（`0x50`）に実測値を入れて辻褄を合わせる形になる。
- **設定が電源断で残るかどうかが分からない。** 円周とパルス数はライブラリから読み返せるので
  firmware が保持しているのは確かだが、不揮発かどうかはどの資料にも書かれていない（**未確認**）。
- **エンコーダ電源の仕様（電圧・電流）、入力の許容周波数、信号レベル（オープンコレクタ可否）は
  資料に無い。** 製品ページの仕様表に「Sampling Accuracy: 12-bit」という記述があるが、
  エンコーダユニットの何を指すのか不明なので本ガイドでは採用しない。

## 早見表

| 電源 | 5V（Grove の赤） |

| バイト順 | 32bit 値はすべてリトルエンディアン（LSB first） |

## レジスタ

| アドレス | 長さ | R/W | 意味 |
|---|---|---|---|
| `0x00` | 4 | R | エンコーダの累計値。32bit、**4 バイト LSB first**。単位はパルス（逓倍後） |
| `0x10` | 4 | R | 距離。32bit、**4 バイト LSB first**、**単位 mm** |
| `0x20` | 9 | R | 同じ距離を firmware が整形した ASCII 9 バイト、**単位 m**。並びは 符号, 千の位, 百の位, 十の位, 一の位, `.`, 1/10, 1/100, 1/1000 |
| `0x30` | 1 | W（PDF では W） | `1` を書くと**エンコーダ値と距離の両方**を 0 に戻す |
| `0x40` | 4 | R/W | 車輪の円周。32bit、**4 バイト LSB first**、**単位 mm** |
| `0x50` | 4 | R/W | 1 回転あたりのパルス数。32bit、**4 バイト LSB first** |
| `0x60` | 4 | R/W | Z パルスの回数（= 回転数）。32bit、**4 バイト LSB first**。書き込んで初期値を与えられる |
| `0x70` | 1 | W（PDF では W/R） | Z パルスの扱い。`0` = 何もしない（連続計数） / `1` = Z の立ち上がりでエンコーダ値を 0 に / `2` = Z の立ち下がりでエンコーダ値を 0 に |
| `0xFE` | 1 | R | ファームウェアのバージョン |
| `0xFF` | 1 | R/W | I2C アドレス。**書くと即時に切り替わる** |

`0x10` と `0x20` は同じ距離の 2 つの見え方で、**単位が違う**（`0x10` は mm、`0x20` は m）。
ASCII 側は小数 3 桁なので分解能は同じ 1mm である。

**転送の形**: 書き込みは「ポインタバイト + ペイロード」を 1 トランザクションで送る。
読み出しはポインタバイトを書いて **repeated START**（`endTransmission(false)`）を打ち、続けて
必要な長さを要求する。ただし `getFirmwareVersion()` と `getI2CAddress()` の 2 つだけは
repeated START ではなく STOP を挟む。firmware はどちらの形でも受け付けているらしい。

## 典型的な使い方

1. `0xFE` を読んでファームウェアのバージョンを確認する（通信確認も兼ねる）。
2. **距離が欲しいなら、先に `0x40`（円周[mm]）と `0x50`（1 回転のパルス数）を書く。**
   ここを設定しないと `0x10` / `0x20` は意味のある値にならない。
3. Z 相を使うなら `0x70` にモードを書く。使わないなら `0`。
4. `0x30` に `1` を書いて起点を作る。
5. あとは `0x00`（パルス）か `0x10`（mm）を周期的に読む。回転数が要るなら `0x60` も読む。
6. 起点を取り直したいときは、`0x30` に `1` を書く。回転数だけ 0 にしたいなら `0x60` に 0 を書く。

## 利用上の注意

- **エンコーダ値は符号付きとして扱う必要がある。** ライブラリは `0x00` / `0x10` / `0x60` を
  すべて `uint32_t` で返す。逆方向に回すと値は 0 を下回り、`uint32_t` では
  4294967295 付近の巨大な数として見える。**受け取ったら `int32_t` に読み替えること。**
  32bit のビット列は同じなので、キャストで済む。
- **`0x20` は NUL 終端されない。** 9 バイトすべてが文字（符号・数字・小数点）で、終端の
  余地が無い。ライブラリの `getMeterString(char *str)` は 9 バイトを丸ごと `memcpy` するので、
  **呼び出し側は 10 バイト以上のバッファを用意して自分で終端を付ける**。`char buf[9]` を
  渡して `printf("%s")` すると読み過ぎる。
- **距離レジスタは導出値である。** `0x10` / `0x20` は `0x40`（円周）と `0x50`（パルス数）から
  計算されている。実際に付いている車輪と設定が食い違えば、値はそのぶん間違う。
  デバイスは食い違いを検出しない。
- **Z のクリアモードを使うと `0x00` が勝手に 0 に戻る。** `0x70` が `1` か `2` のとき、
  エンコーダ値は 1 回転ごとにリセットされる。**`0x00` だけを見ていると「回っているのに
  値が増えない」ように見える。** このモードでは累計は `0x60`（回転数）と `0x00`（回転内の位置）の
  組で表現される。
- **設定が電源断で残るか分からない。** 電源投入のたびに `0x40` / `0x50` / `0x70` を書き直すのが
  安全である。
- **アドレス変更は即時反映。** `0xFF` に書いた次のトランザクションはもう新アドレス宛に
  出さないと応答しない。書き換えた値を忘れると `0x59` を探しても見つからないユニットが
  手元に残る。復旧は scan で全アドレスを舐めることになる。
- **`0x30` と `0x70` はライブラリが読み返さない。** そのため profile では write として
  記録してある。ベンダーの表は `0x70` を W/R としているので firmware は読めるかもしれないが、
  **未確認**である。
- **ライブラリのバグ: I2C 速度が化ける。** `UNIT_EXT_ENCODER` のメンバは `uint8_t _speed;` なのに、
  `begin()` は `uint32_t speed = 100000L` を受け取ってそこへ代入する。100000 は 8bit に
  切り詰められて **160** になり、その値がそのまま `Wire.begin(sda, scl, 160)` に渡る。
  つまり既定の呼び方（ベンダーのサンプルを含む）をすると、**バスが 100kHz ではなく 160Hz に
  設定される**。ホスト側で改めて `Wire.setClock()` を呼ぶか、ライブラリを直すこと。
  デバイスの仕様ではなくライブラリの都合である。
- **ライブラリのバグ: 一部のメソッドがグローバルの `Wire` から読む。**
  `getFirmwareVersion()` と `getI2CAddress()` は書き込みを `_wire` で行うのに、読み出しだけ
  `Wire.read()`（グローバル）を使っている。`begin()` に `Wire1` を渡した構成では、
  この 2 つだけ別のバスから読もうとして壊れる。
- **速いパルス列を取りこぼす可能性は firmware 側にある。** 入力の許容周波数はどの資料にも
  無い（**未確認**）。ホスト側のポーリング周期は計数そのものには影響しないが、
  32bit のラップアラウンドを跨ぐような長時間の放置には注意する。

## 出典と確度

- レジスタのアドレスと転送長: `M5Unit-ExtEncoder` ライブラリのソース
  （`collection/vendor/M5Unit-ExtEncoder` に commit 固定で取得）。
- 単位（`0x10` = mm、`0x20` = m、`0x40` = mm）、`0x20` の 9 バイトの桁の並び、
  `0x30` がエンコーダ値と距離の両方を消すこと、`0x60` が「Turns (Z Counter)」であること、
  `0x70` の 3 値の意味: ベンダーの Unit ExtEncoder I2C Protocol PDF。
  **ライブラリのソースにはこれらの単位・意味の記述が無い。**
- 転送長・アクセス方向・バイト順: ライブラリのメソッド本体から起こした**推定**。
- **文書のバージョン表記の食い違い**: [`chips/m5stack-mcu-u161.yaml`](../../chips/m5stack-mcu-u161.yaml)
  はこの PDF を「firmware version V1 向け」と注記しているが、PDF の表題は
  「V2 (FW Version) 2023/5/10」である。手元のユニットの `0xFE` の値と照らして確認する必要がある
  （**未確認**）。
- **PDF 側の誤り**: PDF の表は Firmware Version と I2C Address の両方を `0xF0` と書いている。
  1 つのアドレスに 2 つのレジスタは置けない。ライブラリの `0xFE` / `0xFF` が正しいとみて
  本文はそちらを採った（M5Stack の他ユニットの protocol PDF にも同じ誤植がある）。
- **未確認**: 実機のキャプチャがまだ無い。設定の不揮発性、入力の許容周波数、
  逓倍の扱い、`0x30` / `0x70` が読めるか、400kHz で動くかは確かめられていない。
- **未調査**: 書き込み側の挙動全般（リセット、円周・パルス数・回転数の設定、Z モード、
  アドレス変更）は probe が read-only のため触れていない。
