# Unit Encoder (U135) — ロータリーエンコーダ入力ユニット

> つまみを回した量と押し込みを I2C 1 本で読み、RGB LED を 2 個光らせられる入力デバイス。
> 返るのは電源投入以降の**累積カウントだけ**で、差分は自分で計算する。
>
> **確度**: M5Stack が Unit Encoder I2C Protocol という PDF（V1 firmware 向け、2022-05-13）を
> 公開しており、レジスタの配置・ボタンの極性・LED インデックスの意味はそこに書かれている。
> ただし `profiles/` に入っているマップは **`M5Unit-Encoder` ライブラリ v0.0.2 のソースから起こした
> 推定**（`evidence: inferred / tentative`）で、実測では未確認。転送長とバイト順の根拠は
> ライブラリのメソッド本体である。

## これは何か

30 位置のロータリーエンコーダ（押し込みスイッチ付き）と SK6812 RGB LED 2 個を、STM32F030F4P6 に
載せた M5Stack ファームウェアが束ねているユニット。**ホストから見える I2C の相手は STM32 であって、
エンコーダでも LED でもない。** つまりレジスタマップはこの製品固有のものである。

本体は 32.0 × 24.0 × 25.4 mm、7.4g、5V@17mA。つまみを 1 周回すと 30 パルス出る。

できること:

- **回転量を累積カウント**として読める（符号付き 16bit）。
- **押し込みスイッチの状態**を読める。
- **RGB LED 2 個の色**を、1 個ずつでも 2 個まとめてでも指定できる。
- ベンダー PDF によれば **モード切り替え**（Pulse / AB）もある。ライブラリは触らない（後述）。

できないこと・持っていないもの:

- **割り込み線は無い。** 変化を知るにはポーリングするしかない。
- **相対値（差分）レジスタが無い。** Unit Scroll や Unit 8Encoder には「前回読んでからの差分」が
  あるが、このユニットには無い。差分はホスト側で前回値を覚えて引き算する。
- **カウンタをリセットするレジスタが無い。** 「1 を書いたら 0 に戻る」ようなレジスタは公開されて
  いない。原点を作りたいなら、そのときのカウント値をホスト側で基準として覚えておく。
- **カウンタに値を書き込めるかどうかが不明。** ライブラリは読むだけで、ベンダー PDF には R/W の
  欄が無い。**未確認**。
- **I2C アドレスを変更できない。** アドレス変更レジスタがマップに存在しない。つまり
  **同じバスに 2 個以上ぶら下げられない**。
- **ファームウェアのバージョンを読むレジスタも無い。** 個体のファーム世代を I2C から知る術が無い。
- **回転の速度・加速度は返らない。** 必要ならホスト側で時間差から求める。

## 早見表

| 項目 | 値 |
|---|---|
| I2C アドレス | `0x40`（**固定**） |
| アドレス変更 | **できない**（レジスタが無い）。複数台を使うなら別バスか I2C マルチプレクサ |
| 電源 | 5V@17mA（Grove の赤） |
| インタフェース | Grove HY2.0-4P（黒=GND、赤=5V、黄=SDA、白=SCL） |
| I2C 速度 | ライブラリは **200kHz** でバスを開く。上限は未実測 |
| 中身 | STM32F030F4P6 + 30 位置ロータリーエンコーダ（押し込みスイッチ付き） + SK6812 ×2 |
| 分解能 | 30 パルス / 回転 |
| 寸法 | 32.0 × 24.0 × 25.4 mm、7.4g |
| 割り込み | 無し（ポーリング） |
| バイト順 | **LSB first**（下位バイトが先） |

## レジスタ

| アドレス | 長さ | R/W | 意味 |
|---|---|---|---|
| `0x00` | 1 | 不明 | モード。`0` = Pulse、`1` = AB、既定 `0`。**ライブラリは一切触らず、`profiles/` にも入っていない**（ベンダー PDF にのみ載る） |
| `0x10` | 2 | R | エンコーダの累積カウント。**符号付き 16bit、LSB first**（byte0 = Value L、byte1 = Value H）。単位はカウント（30 カウント = 1 回転）。物理量の単位は資料に**書かれていない** |
| `0x20` | 1 | R | 押し込みスイッチ。**`0` = 離、`1` = 押下**（既定 `0`）。ベンダー PDF が明記している |
| `0x30` | 4 | W | RGB LED。byte0 = **LED インデックス**（`0` = 全部、`1` = LED1、`2` = LED2）、byte1-3 = R, G, B（各 0〜255、既定 `0`） |

ベンダーの REG MAP に載っているのはこの 4 行だけである。アドレス変更もファーム版数も無い。

**転送の形**: 書き込みは「ポインタバイト + ペイロード」を 1 トランザクションで送る。読み出しは
ポインタバイトを書いて **いったん STOP を出し**（`endTransmission()` を引数なしで呼ぶ）、それから
`requestFrom` でデータフェーズに入る。**repeated START ではない。**

## 典型的な使い方

1. バスを 200kHz 以下で開く（ライブラリの `begin()` は無条件に 200kHz を設定する。後述）。
2. `0x10` を 2 バイト読み、LSB first で `int16_t` として組み立てる。これが現在の累積カウント。
3. 前回読んだ値との差を `int16_t` の引き算で取れば、その間の回転量になる。
4. 押し込みは `0x20`。`1` が押下。
5. LED を光らせるなら `0x30` に `{index, R, G, B}` の 4 バイトを書く。`index` に `0` を書くと
   2 個とも同じ色になる。

## 利用上の注意

- **アドレスが固定で変えられない。** マップにアドレスレジスタが無いので、**同じ I2C バスに
  2 個は繋げない**。2 個以上使うなら、別の I2C ペリフェラルを使うか、PCA9548A / TCA9548A の
  ような I2C マルチプレクサを挟む。ここは Unit Scroll や Unit 8Encoder（どちらもアドレス変更可）
  との大きな違いで、設計段階で効いてくる。
- **相対値が無いので、差分はホストが管理する。** 前回値を保持するのは呼び出し側の責任。
  ポーリングを止めている間の回転も累積には入っているので、取りこぼしはしない（ここは
  読み取りで消費される Unit Scroll の相対値より安全）。
- **16bit なので ±32767 でラップする。** 飽和しない。差分を取るときに `int16_t` 同士で引き算
  すれば、ラップをまたいでも符号付きの折り返しで正しい差が出る。`int32_t` に広げてから引くと
  ラップの瞬間に 65536 のジャンプが出る。
- **押し込みは `1` が押下。** アクティブ Low **ではない**。同じ M5Stack でも Unit Scroll や
  Unit Scales のボタンレジスタはアクティブ Low なので、**他のユニットの経験で反転させると
  逆になる**。根拠はベンダー PDF の明記（`0: Released / 1: Pressed`）とライブラリが反転せずに
  返していることの一致。実測では未確認。
- **`0x30` の byte0 は色ではなくインデックス。** 4 バイトのうち色は byte1-3。`index = 0` は
  「全部」を意味するので、LED1 だけを光らせたいときに `0` を書くと 2 個とも光る。
- **モードレジスタ `0x00` は資料にだけ存在する。** ベンダー PDF には `Mode: 0: Pulse / 1: AB` と
  あるが、ライブラリにも `profiles/` にも無い。**Pulse と AB で `0x10` の増え方がどう変わるかの
  説明は資料に無く、未確認。** 既定（`0`）のまま触らないのが安全。なお PDF の表には行ごとの
  ベースアドレスが印字されておらず、Mode = `0x00` は「4 行が `0x00` / `0x10` / `0x20` / `0x30` の順に
  並ぶ」というライブラリの `#define` との突き合わせから導いた**推定**である。
- **ライブラリが勝手にバス速度を 200kHz に変える。** `Unit_Encoder::begin()` は無条件に
  `Wire.begin(sda, scl, 200000)` を呼ぶ。同じバスに 100kHz までのデバイスがぶら下がっていると
  そちらが壊れる。**後から `begin()` した方の設定が勝つ**ので、初期化の順序で挙動が変わる。
  混在バスなら `begin()` の後に自分で `Wire.setClock()` を呼び直す。
- **`begin()` は疎通確認をしない。** 戻り値も無く、ユニットが繋がっていなくても成功したように
  見える。存在確認をしたいなら自分でアドレスを叩く。
- **読み出しの合間に STOP が入る。** repeated START を前提にバスを解析していると、想定と違う
  波形に見える。マルチマスタ環境では、STOP と次の START の間に他のマスタが割り込む余地がある。
- **本リポジトリの characterization probe は read-only。** LED（`0x30`）とモード（`0x00`）は
  書き込みなので触っていない。

## 出典と確度

- レジスタのアドレスと意味: `M5Unit-Encoder` ライブラリ v0.0.2 のソースから起こした**推定**。
  ベンダーの Protocol PDF とも突き合わせ、`0x10` の L/H の並び（LSB first）、ボタンの極性
  （`1` = 押下）、LED インデックスの意味（`0` = 全部）が一致することを確認した。
- モードレジスタ `0x00`: ベンダー PDF にのみ存在。ライブラリが触らないため `profiles/` には
  入っていない。アドレスは行の並びからの**推定**、動作の意味は**未確認**。
- 転送長・アクセス方向・STOP を挟む読み出し・200kHz: 同ライブラリのメソッド本体から起こした
  **推定**。
- **未確認**: 実機のキャプチャがまだ無い。`0x10` に書き込めるか、モードを切り替えたときの挙動、
  未使用アドレスの振る舞い、バス速度の上限は確かめられていない。
- **未調査**: 書き込み側（LED、モード）は probe が read-only のため触れていない。
