# Unit HBridge v1.1 (U160-V11) — DC モータ用 H ブリッジドライバ（電流検出付き）

> [Unit HBridge (U160)](m5stack-mcu-u160.md) の改版。レジスタマップは v1.0 と同じで、
> **電流検出（`0x30`）とブートローダ移行（`0xFD`）の 2 つだけが増えている**。
>
> **⚠️ これは出力デバイスである。書き込むとモータが回る。** 実験する前に負荷（モータ）を
> 外すこと。本リポジトリの probe が read-only なのは、まさにこの理由による。
>
> **確度**: [`profiles/m5stack-mcu-u160-v11.yaml`](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/profiles/m5stack-mcu-u160-v11.yaml) の
> レジスタマップは `M5Unit-Hbridge` ライブラリのソースから起こした推定
> （`evidence.source: inferred` / `confidence: tentative`）で、**実測では未確認**。
> ベンダーは protocol PDF を出しておらず、製品ページに貼られた画像 1 枚（firmware V2、
> 2023-04-27）がレジスタ表のすべてである。実機のキャプチャはまだ無い。

## これは何か

DC モータドライバ IC（RZ7899）と STM32F030F4P6 を載せたユニット。v1.0 との違いは、
ベンダーの説明では「回路の最適化と電流検出機能の追加」で、電流検出には INA199A1DCKR が
使われている。基板の外形・端子・アドレス・駆動能力は v1.0 と同じ（最大 12V / 3A、
HT3.96-4P ねじ端子、Grove、`0x20`〜`0x2F`）。

ホストから見えるのは STM32 であって、ドライバ IC でも電流センサでもない。**つまり I2C の相手は
固定機能 IC ではなくファームウェアであり、レジスタマップはこの製品固有のもの**である。

できること（v1.0 と共通）:

- 方向を 停止 / 正転 / 逆転 で指定できる。
- PWM デューティを 8bit（0〜255）か 16bit（0〜65535）で指定できる。
- PWM 周波数を 100〜10000Hz で指定できる（既定 1000Hz）。
- 外部入力電圧（VIN）を ADC で読める。8bit と 12bit の 2 通り。
- I2C アドレスを基板上のスイッチで `0x20`〜`0x2F` の 16 通りから選べる。

**v1.1 で増えたこと**:

- **電流を読める**（`0x30`）。値は 32bit の **IEEE 754 単精度 float**、単位は **A（アンペア）**。
  ベンダーのレジスタ表はこの行を「VIN Current」と呼んでいる。ライブラリのメソッド名は
  `getMotorCurrent()` だが、実際に測っているのは**電源入力側の電流**である（電流検出 IC が
  VIN 側に入っている）。モータが回っているときはほぼモータ電流に等しいが、厳密には
  ユニット自身の消費も含む。
- **ブートローダに入れる**（`0xFD`）。ファームウェア更新用。ただし後述のとおり、
  この行はベンダーのレジスタ表には載っていない。

できないこと・持っていないもの（v1.0 と共通）:

- **エンコーダ入力が無い。** 速度も位置もフィードバックできない。
- **割り込み線・エラー通知が無い。** 過電流・過電圧・過熱の保護はドライバ IC 側にあるが、
  **保護が働いたことを知らせるレジスタは無い**。電流値を自分でポーリングして判断するしかない。
- **ソフトウェアでは I2C アドレスを変更できない。** `0xFF` は読み出し専用。
- **電流の校正値・オフセットを読めない。** 返るのは firmware が計算した float 1 つだけで、
  ゼロ点や分解能は分からない。
- **ADC の VIN 値は生の数値で、電圧ではない。** 係数はホスト側で掛ける（後述）。
- **ブレーキとフリーランの区別が無い**（方向の `0` がどちらかは**未確認**）。

## レジスタ

`0x00`〜`0x05` は 1 つの連続した設定ブロックである。**★** が v1.1 だけにあるレジスタ。

| アドレス | 長さ | R/W | 意味 |
|---|---|---|---|
| `0x00` | 1 | R/W | 方向。`0` = 停止（既定） / `1` = 正転 / `2` = 逆転 |
| `0x01` | 1 | R/W | PWM デューティ 8bit。0〜255 |
| `0x02` | 2 | R/W | PWM デューティ 16bit。0〜65535、**2 バイト LSB first** |
| `0x04` | 2 | R/W | PWM 周波数。100〜10000（**単位 Hz**）、既定 1000、**2 バイト LSB first** |
| `0x10` | 1 | R | VIN の ADC 値（8bit）。0〜255。**生の数値で、電圧ではない** |
| `0x20` | 2 | R | VIN の ADC 値（12bit）。0〜4095、**2 バイト LSB first**。**生の数値で、電圧ではない** |
| ★ `0x30` | 4 | R | VIN 電流。**IEEE 754 単精度 float、4 バイトのリトルエンディアン。単位は A** |
| ★ `0xFD` | 1 | W | `1` を書くとファーム更新用ブートローダに入る |
| `0xFE` | 1 | R | ファームウェアのバージョン |
| `0xFF` | 1 | R | 応答している I2C アドレス |

**転送の形**: v1.0 と同じ。書き込みは「ポインタバイト + ペイロード」を 1 トランザクション。
読み出しは repeated START を使わず、**ポインタバイトを書いて STOP を打ち、改めてアドレス
指定して読む 2 トランザクション**になる。

### VIN の電圧への直し方

ライブラリは係数を一切適用しない。ベンダーのサンプルは 12bit 値に対して次の式を使っている。

```
電圧[V] = raw / 4095.0 * 3.3 / 0.09
```

`0.09` は基板上の分圧比で、フルスケールは約 36.7V に相当する。**この係数はサンプルコードに
しか書かれておらず、レジスタ表にも API にも出てこない。**

電流（`0x30`）の方は firmware 側で A に換算済みなので、係数は要らない。

## v1.0（U160）との違い

**同じ 1 つのライブラリ `M5Unit-Hbridge` が両方を担当する。** 差は次の 2 点だけである。

| | v1.0 (U160) | v1.1 (U160-V11) |
|---|---|---|
| `0x30` 電流 | 無し | **あり**（float 4 バイト LE、単位 A） |
| `0xFD` ブートローダ移行 | 無し | **あり**（ライブラリのみ。ベンダーのレジスタ表には無い） |
| その他のレジスタ | — | v1.0 と同一 |
| ファームウェアのバージョン（`0xFE`） | V1 | V2 |

**ライブラリは、どちらのユニットが繋がっているかを判別しない。** `begin()` は該当アドレスに
ACK が返るかを見るだけで、版も firmware バージョンも確認しない。`getMotorCurrent()` と
`jumpBootloader()` のソースに `// Only V1.1 can use this` というコメントが添えられているだけで、
実行時のガードは無い。**v1.0 に対して `getMotorCurrent()` を呼ぶとレジスタ表に無い `0x30` を
読むことになり、何が返るかは未確認である。**

判別が要る場合、ベンダーのサンプルは `getFirmwareVersion() >= 2` を条件にしている。
これはレジスタ表の版表記（v1.0 = V1、v1.1 = V2）と整合するが、**「firmware V2 なら必ず v1.1
基板」と保証した文書は存在しない**。あくまでサンプルコードの流儀である。

## 典型的な使い方

1. **モータを外した状態で** `0xFE` を読み、ファームウェアのバージョンと通信を確認する。
   ここで `2` 以上なら v1.1 とみなす（上記の但し書きつき）。
2. 必要なら `0x04` に PWM 周波数を書く（2 バイト LSB first）。
3. デューティを書く。**8bit（`0x01`）か 16bit（`0x02`）のどちらかに決めて、混ぜない。**
4. `0x00` に方向を書く。**ここで初めてモータが回る。**
5. 回転中は `0x30` を 4 バイト読み、float として解釈して電流[A]を監視する。過負荷や
   拘束の検出はこの値を見るしかない。
6. 止めるときは `0x00` に `0` を書く。
7. 電源電圧を見たいなら `0x20` を 2 バイト読み、上の式で V に直す。

## 利用上の注意

### 安全

- **書き込むとモータが回る。** 台の上でユニットだけを繋いで実験するときは、必ず端子から
  モータを外すか、回っても危なくない状態にすること。
- **モータは誘導性負荷である。** 停止・反転の瞬間に逆起電力が発生する。電源側に十分な容量の
  コンデンサを置き、電源ラインを長く引き回さないこと。
- **正転から逆転へ直接切り替えられてしまう。** レジスタは `1` → `2` の書き込みを拒まない。
  高速回転中に反転を書くと、モータと電源に大きな電流が流れる。減速を挟むかどうかは
  ホスト側の責任になる。
- **ホストが落ちてもモータは止まらない可能性が高い。** レジスタは書かれた値を保持する設計で、
  ライブラリにもタイムアウトやウォッチドッグの気配は無い。firmware 側に停止機構があるかは
  **未確認**。ホストのリセットで暴走させたくないなら、外部電源を切れるようにしておく。
- **外部入力は最大 12V、電流は最大 3A。** これを超える電源やモータを繋がない。
- **`0xFD` に書くとブートローダに入る。** 通常のアプリケーションから触る理由は無い。
  誤って書くと I2C の応答が変わり、モータ制御も効かなくなる。書き込み先を計算で組み立てる
  コードでは特に注意する。
- **本リポジトリの probe（`scenarios/m5stack-mcu-u160-v11/p0.yaml`）は `safety: read-only`。**
  書き込みレジスタは 1 つも叩かない。

### プロトコル

- **電流は整数ではない。** `0x30` の 4 バイトは firmware が持っている float のバイト列
  そのままで、ライブラリは `memcpy()` で `float` に流し込むだけである。したがって
  **リトルエンディアンの IEEE 754 binary32 として解釈する**。ホスト側の float 表現が
  違う環境（ビッグエンディアン等）では、ライブラリのままでは正しい値にならない。
- **`getMotorCurrent()` が測るのは VIN 側の電流。** ベンダーのレジスタ表の行名は
  「VIN Current」であり、モータ巻線の電流と厳密に同じではない。
- **方向とデューティは独立している。** デューティを書いてもモータは回らない。`0x00` に
  `1` か `2` を書いて初めて回る。
- **8bit デューティと 16bit デューティは別レジスタである。** 両方に書いたときにどちらが
  有効かは、ライブラリからもレジスタ表からも判断できない（**未確認**）。
  **どちらか一方に決めて使うこと。**
- **多バイト値はすべて LSB first。**
- **ADC の VIN 値には係数が要る。** 生の数値をそのまま V として表示しない。
- **読み出しに repeated START を使わない。** ポインタバイトの書き込みと読み出しの間に STOP が
  入る。バス共有時は注意。
- **ライブラリのバグ: I2C 速度が化ける。** `M5UnitHbridge` のメンバは `uint8_t _speed;` なのに、
  `begin()` は `uint32_t speed = 100000L` を受け取ってそこへ代入する。100000 は 8bit に
  切り詰められて **160** になり、その値がそのまま `Wire.begin(sda, scl, 160)` に渡る。
  つまり既定の呼び方（ベンダーのサンプルを含む）をすると、**バスが 100kHz ではなく 160Hz に
  設定される**。ホスト側で改めて `Wire.setClock()` を呼ぶか、ライブラリを直すこと。
- **`0xFD` はベンダーのレジスタ表に載っていない。** ライブラリの `jumpBootloader()` だけが
  出典である。v1.1 の表に載っているのは `0x30` の追加までで、`0xFD` の存在は**未確認**。
- **アドレスはハードウェアで決まる。** `0xFF` は読むだけ。応答が無いときは `0x20`〜`0x2F` を
  scan する。

## 出典と確度

- レジスタのアドレスと転送長: `M5Unit-Hbridge` ライブラリのソース
  （`collection/vendor/M5Unit-Hbridge` に commit 固定で取得）。
- v1.0 との差が `0x30` と `0xFD` の 2 つだけであること: ライブラリのソース中の
  `// Only V1.1 can use this` コメントが根拠。ベンダーのレジスタ表の画像も、v1.1 の表に
  `0x30`（VIN Current, float）が 1 行増えているだけで他は同一である。
  ただし**`0xFD` はベンダーの表には無い**。
- 値域（方向 0/1/2、デューティ、PWM 周波数 100〜10000Hz・既定 1000Hz、ADC 0〜4095）、
  行名「VIN Current」、`0x20`〜`0x2F` のアドレス選択スイッチ: ベンダーが製品ページに
  貼っているレジスタ表の**画像**から読み取った。**この製品には protocol PDF が無い。**
- 電流が float でリトルエンディアンであること: ライブラリが 4 バイトを `memcpy()` で
  `float` に流し込んでいることからの**推定**。表にも `float` とだけ書かれている。
- ADC → 電圧の係数（`/4095 * 3.3 / 0.09`）: ベンダーのサンプルコードのみが出典。
- **未確認**: 実機のキャプチャがまだ無い。`0xFD` が実在するか、8bit と 16bit のデューティを
  両方書いたときの優先順位、`0` が電気ブレーキかフリーランか、電流のゼロ点・分解能、
  ホストが黙ったあとの firmware の挙動、400kHz で動くかは確かめられていない。
- **未調査**: 書き込み側の挙動全般（方向・速度・周波数・ブートローダ移行）は probe が
  read-only のため触れていない。これは意図的な制限であり、書き込みがモータを回すためである。
