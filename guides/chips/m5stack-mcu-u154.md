# Unit 8Angle (U154) — 8 連ポテンショメータ入力ユニット

> ツマミ 8 個・トグルスイッチ 1 個・RGB LED 9 個を、I2C のレジスタ読み書きとして
> 扱えるようにした入力デバイス。バスの相手は固定機能 IC ではなく、ユニット上の
> STM32F030 で動くファームウェアである。
>
> **確度**: [`profiles/m5stack-mcu-u154.yaml`](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/profiles/m5stack-mcu-u154.yaml) の
> レジスタマップは `M5Unit-8Angle` ライブラリのソースから起こした推定
> （`evidence.source: inferred` / `confidence: tentative`）で、**実測では未確認**。
> 本文はベンダーの 8Angle I2C Protocol PDF（firmware V1、2022-11-10）とも突き合わせてあり、
> 両者が食い違う点は本文中に明記した。実機のキャプチャはまだ無い。

## これは何か

回転式ポテンショメータ（可変抵抗のツマミ）8 個、トグルスイッチ 1 個、RGB LED（SK6812-3535）
9 個を、STM32F030F4P6 に載せた M5Stack ファームウェアが束ねているユニット。ホストから見える
のは STM32 であって、ポテンショメータでも LED でもない。**つまり I2C の相手は固定機能 IC では
なくファームウェアであり、レジスタマップはこの製品固有のもの**である。

LED が 9 個でツマミが 8 個なのは、8 個がツマミに対応し、残る 1 個がトグルスイッチ用だから。

用途は「物理ツマミ 8 本のコントロールパネル」。ミキサー、色の調整、パラメータ入力など、
値をアナログで与えたい場面に向く。

できること:

- 8 本のツマミの位置を **12bit（0〜4095）** または **8bit（0〜255）** で読める。この 2 つは
  同じ 8 本の別の見え方であって、別のセンサではない。
- トグルスイッチの状態（0 か 1）を読める。
- LED 9 個それぞれの R, G, B と明るさを指定できる。
- I2C アドレスを変更できる（複数台を同じバスに並べられる）。

できないこと・持っていないもの:

- **割り込み線は無い。変化を知るにはポーリングするしかない。**
- **角度は返さない。** 返るのは ADC の生の値であって、度でもパーセントでもない。両端の値が
  0 と 4095 になる保証も資料には無いので、端点の校正はホスト側で行う。
- **校正値の読み出しが無い。** ツマミの機械的な可動範囲・デッドゾーンは firmware から読めない。
- ADC の基準電圧、分解能の実効値、サンプリング周期、平滑化の有無はどの資料にも書かれていない。
- ライブラリには**アドレスを読み戻す手段が無い**（`getI2CAddress()` に相当するメソッドが無い）。
  PDF はアドレスレジスタを R/W としているが、ライブラリからは書きっぱなしになる。
- LED の現在値をライブラリから読み戻せない（PDF は R/W だが読み出しメソッドが無い）。

## レジスタ

| アドレス | 長さ | R/W | 意味 |
|---|---|---|---|
| `0x00` | 16 | R | 12bit ADC ブロック。ch *n* は `0x00 + n*2`、2 バイト **LSB first**、値 0〜4095。上位バイトの上位 4bit は未使用 |
| `0x10` | 8 | R | 同じ 8 本を 8bit で。ch *n* は `0x10 + n`、1 バイト、値 0〜255 |
| `0x20` | 1 | R | トグルスイッチ。値は 0 か 1。**どちらが ON かはどの資料にも書かれていない（未確認）** |
| `0x30` | 36 | W（PDF では R/W） | RGB LED 9 個。LED *n* は `0x30 + n*4`、4 バイトで R, G, B, 明るさ。R/G/B は 0〜255、**明るさは 0〜100** |
| `0xFE` | 1 | R | ファームウェアのバージョン |
| `0xFF` | 1 | W（PDF では R/W） | I2C アドレス。値 0〜127、既定 `0x43` |

LED ブロックは PDF 上では 3 行に分かれている（`0x30` が LED0〜3、`0x40` が LED4〜7、
`0x50` が LED8）が、`0x30 + n*4` という 1 本の連続ブロックとして数えても同じ配置になる。
LED8 が `0x50` に来るのはそのため。

**転送の形**: 書き込みは「ポインタバイト + ペイロード」を 1 トランザクションで送る。
読み出しは repeated START を使わず、**ポインタバイトを書いて STOP を打ち、改めて
アドレス指定して読む 2 トランザクション**になる。

## 典型的な使い方

1. `0xFE` を読んでファームウェアのバージョンを確認する（通信が成立しているかの確認も兼ねる）。
2. ツマミを読む。UI の粗い操作なら `0x10 + ch` の 1 バイト、分解能が要るなら
   `0x00 + ch*2` の 2 バイトを読む。8 本まとめて欲しいなら `0x00` から 16 バイト、
   `0x10` から 8 バイトを 1 回で読めばよい（ライブラリは 1ch ずつしか読まない）。
3. トグルスイッチは `0x20` を読む。値の意味は自分で確かめる。
4. LED を光らせるなら `0x30 + n*4` に `{R, G, B, 明るさ}` を書く。*n* は 0〜8。
5. 複数台を並べるなら `0xFF` に新しいアドレスを書く。**書いた瞬間から新アドレスになる。**

## 利用上の注意

- **明るさは 0〜100 で、0〜255 ではない。** PDF は `BR:0~100` と明記している。ライブラリは
  `bright & 0xff` をそのまま送るので 255 まで通ってしまうが、100 を超えたときの挙動は
  どこにも書かれていない。色は 0〜255、明るさだけ 0〜100 という非対称に注意。
- **`0x30` の 4 バイト目は色ではなく明るさ。** 32bit の色を `0xRRGGBB` として渡す API に
  引きずられて 4 バイト目を無視すると、明るさが 0 のまま光らない。
- **ライブラリの LED 番号ガードが 1 つ甘い。** `M5_ANGLE8::setLEDColor()` は
  `if (ch > ANGLE8_TOTAL_LED) return false;` で、`ANGLE8_TOTAL_LED` は 9。`>=` ではなく `>` なので
  **`ch = 9` が通る**。`ch = 9` は `0x30 + 36 = 0x54` を叩くが、そこは PDF の表に無い。
  実在する LED は 0〜8 の 9 個なので、上限は自分で 8 に切ること。
- **ADC のチャンネル番号にはガードが無い。** `getAnalogInput(ch, ...)` は `ch` を一切検査せず
  `0x00 + ch*2` / `0x10 + ch` を組み立てる。`ch = 8` を渡すと 12bit 側は `0x10`（= 8bit ブロックの
  先頭）を、8bit 側は `0x20`（= スイッチ）を読む。**範囲外でも NACK にならず、それらしい値が返る**
  ので、間違いに気づけない。
- **12bit 値は LSB first。** `data[1] << 8 | data[0]` で組み立てる。上位バイトの上位 4bit は
  未使用なので、符号拡張やマスクを掛けると壊れる。
- **アドレス変更は即時反映で、読み戻す手段が無い。** `0xFF` に書いた次のトランザクションは
  もう新アドレス宛に出さないと応答しない。ライブラリに `getI2CAddress()` が無いので、
  書き換えた値を忘れると `0x43` を探しても見つからないユニットが手元に残る。復旧は
  scan で全アドレスを舐めることになる。
- **読み出しに repeated START を使わない。** ポインタバイトの書き込みと読み出しの間に STOP が
  入るので、その隙に同じバスの別トランザクションが割り込むとポインタが失われる可能性がある。
  マルチマスタ構成やバス共有時は注意。
- **このライブラリはグローバルの `Wire` しか使わない。** `begin()` の引数はアドレスだけで、
  内部で `_wire = &Wire;` と決め打ちし、さらに `_wire->begin()` をピン指定無しで呼ぶ。
  Wire1 側のポートに挿したユニットは、このライブラリのままでは扱えない。
- **`writeBytes()` は必ず `true` を返す。** `endTransmission()` の戻り値を見ていないので、
  `setLEDColor()` や `setDeviceAddr()` の戻り値は「送った」以上の意味を持たない。
  ユニットが外れていても成功に見える。
- **割り込みが無いので、ツマミを速く回した途中の値は残らない。** 絶対値なので最新値は
  常に正しく読めるが、動きの軌跡が要るならポーリング周期を詰めるしかない。

## 出典と確度

- レジスタのアドレスと意味: `M5Unit-8Angle` ライブラリのソース
  （`collection/vendor/M5Unit-8Angle` に commit 固定で取得）。
- 値域（ADC 0〜4095 / 0〜255、明るさ 0〜100、アドレス 0〜127、既定 `0x43`）、および
  LED8 の存在: ベンダーの 8Angle I2C Protocol PDF（V1、2022-11-10）。ライブラリのソースには
  値域の記述が無く、これは PDF だけが持っている情報である。
- 転送長・アクセス方向・バイト順・チャンネル間隔: ライブラリのメソッド本体から起こした**推定**。
- **ライブラリと PDF の差**: PDF は LED ブロックとアドレスレジスタを R/W としているが、
  ライブラリには読み出しメソッドが無い。profile はライブラリに合わせて write として
  記録している。firmware が実際に読めるかは**未確認**。
- **PDF 側の誤り**: PDF の表は Firmware Version と I2C Address の両方を `0xF0` と書いている。
  1 つのアドレスに 2 つのレジスタは置けない。ライブラリの `0xFE` / `0xFF` が正しいとみて
  本文はそちらを採った（M5Stack の他ユニットの protocol PDF にも同じ誤植がある）。
- **未確認**: 実機のキャプチャがまだ無い。トグルスイッチの 0/1 がどちらの向きか、
  未使用アドレスがどう振る舞うか、400kHz で動くかは確かめられていない。
- **未調査**: 書き込み側の挙動全般（LED、アドレス変更）は probe が read-only のため触れていない。
