# SHT40 — 温湿度センサ（SHT4x ファミリの標準精度品）

> SHT3x の後継世代。コマンドが 16bit から **8bit** に変わり、クロックストレッチが廃止され、
> ヒータが「電力 × 時間」を選ぶ単発コマンドになった。応答は 16bit ワード + CRC-8 のままである。
>
> **確度**: Sensirion の datasheet（SHT4x, D1 Version 6.4, 2023-11）に基づく。**実測は無い**。
> `observations/sht40/` は存在せず、[`profiles/sht40.yaml`](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/profiles/sht40.yaml) の
> `evidence` も `source: datasheet` / `confidence: tentative` である。

## これは何か

Sensirion の第 4 世代の温湿度センサ。1 個の DFN パッケージに湿度素子・温度素子・A/D・補正演算・
I2C が入っており、出荷時に個体ごとに校正されている。ホストは補正係数を読む必要がなく、
16bit の生値を式に入れるだけで ℃ と %RH になる。個体ごとのシリアル番号を OTP に持ち、
`0x89` で 16bit ワード 2 個（計 32bit）として読める（SHT3x には無かった）。

SHT40 はファミリの**標準精度品**で、SHT41 / SHT45 は同じコマンドセットのまま精度が高い。
SHT43 は ISO17025 の 3 点校正証明書付き。ソフトウェアから見た差は無い。

SHT3x（SHT30）との実務上の違い:

| | SHT30（SHT3x-DIS） | SHT40（SHT4x） |
|---|---|---|
| コマンド長 | 16bit（コマンド自体に 3bit CRC） | **8bit（CRC なし）** |
| クロックストレッチ | 単発測定で選べる | **無い。busy 時は読み出しヘッダを NACK** |
| 電源 | 2.15〜5.5 V | **1.08〜3.6 V。5 V を直結できない** |
| アドレス | ADDR ピンで `0x44` / `0x45` | **注文時の型番で固定**（`0x44` / `0x45` / `0x46`） |
| ヒータ | ON / OFF のトグル | **電力 3 段 × 時間 2 段の単発コマンド。自動で切れる** |
| シリアル番号 | 無し | `0x89` で 32bit |
| 周期測定モード | ある（0.5〜10 mps） | **無い。毎回コマンドを送る** |
| 測定時間（high） | 12.5 ms typ | **6.9 ms typ** |

できること:

- 単発測定を high / medium / low の 3 段で。返るのは温度 → 湿度の順（SHT3x と同じ順序）。
- ヒータを 20 / 110 / 200 mW × 0.1 / 1 s の 6 通りで焚き、**その直後の high 精度測定まで含めて**
  1 コマンドで実行する。
- シリアル番号の読み出し。個体識別と存在確認を兼ねられる。
- ソフトリセットと general call リセット。実行中のコマンドの中断にも使える。

できないこと・持っていないもの:

- **周期測定モードが無い。** 1 サンプルごとにコマンドを送る。「開始したら勝手に更新し続ける」
  使い方はできない。
- **クロックストレッチが無い。** datasheet が明記している（4.1 節）。ストレッチ前提で書かれた
  ドライバをそのまま持ってくると、待ちが入らずに NACK を食う。
- **データレディを知らせるピンが無い。** ALERT ピンも nRESET ピンも無い（4 ピン）。
- **測定値は 1 回しか読めない。** 最初に ACK された読み出しでレジスタから消える。
- **アドレスを変える手段が無い。** ピンもコマンドも無く、型番（A / B / C）で決まっている。
  同じバスに 2 個並べたければ、別の型番を買うか I2C マルチプレクサを使う。
- **ヒータを任意の時間 ON にできない。** 最大 1 s で自動的に切れる。OFF コマンドは存在しない。

電気的な現実:

- VDD は **1.08〜3.6 V**。**5 V は絶対最大定格を超える。** SHT30 と同じ感覚で Grove の 5 V に
  繋いではいけない。M5Stack Unit ENV-IV（U001-D）はユニット内で降圧している。
- 測定中 320 µA typ、アイドル 80 nA typ。1 秒に 1 回の high 測定で平均 2.2 µA。
- **ヒータ ON 時は最大 75 mA（200 mW 設定）を引く。** 電源が弱いと電圧降下でセンサ自身が
  リセットする、と datasheet が警告している。
- I2C は standard / fast / fast-mode plus。プルアップは VDD ≥ 1.62 V で 390 Ω 以上が必須条件。

## コマンド

すべて 1 バイト。応答があるものは 6 バイト（16bit ワード 2 個 + それぞれの CRC）。

| コマンド | 応答 | 意味 |
|---|---|---|
| `0xFD` | 6 バイト | 単発測定（high repeatability）。6.9 ms typ |
| `0xF6` | 6 バイト | 単発測定（medium）。3.7 ms typ |
| `0xE0` | 6 バイト | 単発測定（low）。1.3 ms typ |
| `0x89` | 6 バイト | シリアル番号（16bit ワード × 2 = 32bit、各ワードに CRC） |
| `0x94` | ACK のみ | ソフトリセット。1 ms |
| `0x39` | 6 バイト | ヒータ 200 mW を **1 s** 焚いてから high 測定 |
| `0x32` | 6 バイト | ヒータ 200 mW を **0.1 s** 焚いてから high 測定 |
| `0x2F` | 6 バイト | ヒータ 110 mW を 1 s |
| `0x24` | 6 バイト | ヒータ 110 mW を 0.1 s |
| `0x1E` | 6 バイト | ヒータ 20 mW を 1 s |
| `0x15` | 6 バイト | ヒータ 20 mW を 0.1 s |
| `0x06` @ アドレス `0x00` | — | general call reset（**バス上の全デバイスがリセットされる**） |

[`profiles/sht40.yaml`](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/profiles/sht40.yaml) には 0.1 s 版のヒータ（`0x32` / `0x24` / `0x15`）が
入っていない。datasheet Table 8（p.12）が正本である。

**応答フレームの形（Sensirion 共通）**: 応答は「16bit ワード（MSB first）+ CRC-8 1 バイト」の
3 バイト単位で並ぶ。測定なら `[温度上位, 温度下位, CRC, 湿度上位, 湿度下位, CRC]` の 6 バイト。
CRC は**直前の 2 バイトだけ**が対象（多項式 `0x31` = x⁸+x⁵+x⁴+1、初期値 `0xFF`、
入出力ビット反転なし、最終 XOR `0x00`。検算値: CRC(`0xBEEF`) = `0x92`）。SHT3x と完全に同じ規則なので、
CRC の実装は流用できる。**違うのはコマンド側で、SHT4x のコマンドは 1 バイトで CRC を持たない。**

**CRC が落ちたときと、値がおかしいときは別の話である。** CRC 不一致は「バスの上でバイトが壊れた」
という意味で、疑うのはプルアップ・配線・速度・ノイズであってセンサではない。CRC が通っているのに
値が変なら、センサは本当にその値を返している（ヒータの余熱、自己発熱、フレーム境界の取り違え）。
**境界が 1 バイトずれると全ワードの CRC が落ちる**ので、全滅するときはまずフレーム長の解釈を疑う。

**値の変換**（datasheet 4.6 節、式 1〜3）:

- 温度 ℃ = −45 + 175 × S_T / (2¹⁶ − 1)
- 湿度 %RH = **−6** + 125 × S_RH / (2¹⁶ − 1)

温度の式は SHT3x と同一だが、**湿度の式は違う**（SHT3x は 0〜100 の線形、SHT4x は −6〜119）。
SHT3x 用の変換をそのまま使うと湿度だけが系統的にずれる。SHT4x の式は 0 %RH 未満や 100 %RH 超の
値を返しうるので、物理量として使うなら 0〜100 にクリップする（datasheet も推奨している）。
なお 2¹⁶−1 を 2¹⁶ で割っても誤差は < 0.002 %RH / < 0.003 ℃ である。

## 典型的な使い方

1. 電源投入から 1 ms 待つ。
2. `0x89` を送り、6 バイト読む。CRC を検算する。ここで**存在確認と CRC 実装の確認が同時にできる**。
   シリアル番号は OTP に焼かれていて変わらないので、個体の記録にも使える。
3. 測定コマンド（`0xFD` / `0xF6` / `0xE0`）を送る。
4. 測定時間だけ待つ。datasheet の Quick Start（p.3）の疑似コードは `0xFD` に対して **10 ms** の
   固定待ちを使っている（max 8.3 ms に対する安全側の値）。待たずに読んだ場合は NACK が返るので、
   NACK を data-ready の合図として再試行してもよい。
5. 6 バイト読む。各ワードの CRC を検算してから変換する。
6. 次のサンプルが要るなら 3 に戻る。**周期モードは無いので毎回コマンドを送る。**

ヒータを使う場合（結露の除去、高湿度環境でのクリープ抑制）:

1. ヒータコマンド（例 `0x39` = 200 mW / 1 s）を送る。
2. ヒータ ON → タイマ満了 → **その状態のまま high 精度測定** → ヒータ OFF、という順で
   センサが自動実行する。ホストは 1 s + 測定時間だけ待ってから 6 バイト読む。
3. **返ってきた値は加熱中の値である。** 環境の温湿度としては使えない（下記）。
4. 冷えるのを待ってから通常の測定に戻る。

## 利用上の注意

- **ヒータを焚いた直後の測定値は環境の値ではない。** ヒータコマンドが返す 6 バイトは
  「ヒータが入ったまま」測った値で、datasheet も 4.9 節で「ヒータ動作中はセンサの仕様は成立しない」
  「熱による機械的応力で温度出力がさらにずれる」と明記している。用途は結露を飛ばすことであって、
  そのときの温湿度を知ることではない。
- **どれだけ待てば元に戻るか。** datasheet は冷却時間を数値で規定していない。規定されているのは
  **デューティ上限 10%** だけである（4.9 節 / Table 9）。これを守ると、
  **1 s のヒータパルスなら次のパルスまで最低 9 s**、0.1 s なら最低 0.9 s は空けることになり、
  実務上はこれがそのまま「加熱後の待ち時間」の下限になる。復帰の判定は時間ではなく値で行うのが
  確実で、通常測定を 1 s 間隔で繰り返し、**温度が加熱前の水準に戻り、湿度が単調変化を止めるまで**は
  記録に使わない。目安として 1 s / 200 mW のパルスなら 10 秒前後は疑ってかかること
  （この「10 秒前後」はデューティ規定から導いた運用上の目安であり、**datasheet の保証値ではない**）。
- **ヒータの累積 ON 時間はセンサの寿命に効く。** 「総 ON 時間がセンサ寿命の 10% を超えないこと」
  という書き方をしている。定常的に焚く設計にはしない。周囲温度 65 ℃ 以上ではヒータを使わない。
- **クロックストレッチは無い。** ストレッチ前提のドライバを移植すると、コマンド直後の読み出しが
  NACK されて「センサが応答しない」ように見える。正しくは待つか、NACK を見てリトライする。
- **NACK は「まだ測っている」の合図。** 通信エラーとして扱わない（4.1 節 / Table 8 の注記）。
- **測定値は 1 回しか読めない。** 最初に ACK された読み出しでレジスタから消える。同じ値を
  2 回読むと 2 回目は取れない。
- **5 V を掛けない。** 絶対最大定格は VDD + 0.3 V。SHT30（5.5 V まで可）と同じつもりで
  Grove の赤線に直結すると壊れる。ENV-III（SHT30）と ENV-IV（SHT40）を差し替えるときに
  最も危険なのがここである。
- **湿度の変換式が SHT3x と違う。** `−6 + 125 × S/65535`。SHT3x の `100 × S/65535` を使うと
  低湿側で数 %RH ずれる。CRC は通るので気づきにくい。
- **`0x44` に応答があっても SHT40 とは限らない。** SHT30 も既定 `0x44` で、アドレスでは区別できない。
  SHT4x は 8bit コマンドなので、`0x89`（シリアル番号）に 6 バイトで答えるかどうかで見分ける。
  逆に SHT3x なら `0xF32D`（16bit）に答える。
- **アドレスは注文時の型番で決まる。** `SHT40-**A**D1B` が `0x44`、`-**B**D1B` が `0x45`、
  `-**C**D1B` が `0x46`（型番 7 桁目の文字）。基板を見ても分からないので、モジュールの
  ドキュメントか実測で確認するしかない。
- **general call reset（`0x00` + `0x06`）はバス上の全デバイスを巻き込む。** 同居デバイスがある構成では
  `0x94`（ソフトリセット）を使う。
- **CRC を検算せずに使わない。** 6 バイトのうち 2 バイトは CRC である。

## 出典と確度

- コマンド、フレーム、CRC、変換式、タイミング、ヒータ仕様: **SHT4x Datasheet D1 Version 6.4
  （2023-11）**。M5Stack が配布しているのは Version 2（2021-07、17 ページ）で、章立てとページ番号が
  異なる。本ガイドのページ番号はすべて Version 6.4 のもの。
- ヒータ後の「10 秒前後は待つ」という目安は、datasheet のデューティ上限 10%（4.9 節）から
  導いた**運用上の推定**であって、datasheet が規定した冷却時間ではない。**datasheet は加熱後の
  復帰時間を数値で答えていない。**
- **未確認（実測なし）**: `observations/sht40/` は存在しない。アドレス `0x44` の応答、
  シリアル番号の実際の値、測定時間の実測、ヒータの温度上昇量と復帰時間、400 kHz / fast-mode plus
  での動作、いずれも確かめられていない。[`scenarios/sht40/p0.yaml`](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/scenarios/sht40/p0.yaml) では
  ヒータ・クロックストレッチ変種・repeatability の timing sweep が `deferred` になっている。
- **未調査**: SHT41 / SHT43 / SHT45 の実物を持っていないため、「コマンドセットが同一」は
  datasheet の記述に依存している。
