# Unit MQ (U199) — MQ-5 可燃性ガスセンサユニット

> MQ-5 半導体式ガスセンサとサーミスタをマイコンの ADC で読み、ヒータの加熱の仕方まで
> I2C から制御できるようにしたユニット。**返ってくるのは生の ADC 値と電圧であって、
> ガス濃度ではない。**
>
> **確度**: M5Stack が `MQ_I2C_Protocol_EN` という PDF を公開しており、レジスタ表は
> そこと `M5Unit-MQ` ライブラリのソースの両方に存在する。本ガイドは両方を突き合わせて
> 書いた（両者が食い違う箇所は後述する）。ただし `profiles/m5stack-mcu-u199.yaml` の
> evidence は `inferred` / `tentative` のままで、**実測では未確認**。

## これは何か

MQ-5（LPG・メタンなどの可燃性ガス向け）の半導体式ガスセンサを載せたユニット。
MQ 系のセンサはヒータで素子を焼いて動かすアナログ素子で、**I2C バスには繋がっていない**。
基板上の STM32G030F6P6 が、MQ の出力とサーミスタ（NTC）の出力を自分の ADC で読み、
ヒータのオン／オフも自分で制御している。ホストから見えるのはその STM32 のファームウェア
である。したがってレジスタマップはこの製品固有のもので、MQ-5 の datasheet を読んでも
レジスタは出てこない。

半導体式ガスセンサは、素子が温まっていないと値が意味を持たない。このユニットのヒータ
制御は 3 通りある。

- **OFF**（電源投入時の既定）: 加熱しない。ガスの値は無効のまま。
- **連続加熱**: ヒータを入れっぱなしにする。反応は速いが電気を食う。
- **ピンレベル切り替え**: ヒータを一定時間 High、一定時間 Low と繰り返す間欠加熱。
  消費電力を抑えられるが、High の期間の頭は値が使えない。

できること:

- MQ センサの読み値を 8bit（0〜255）と 12bit（0〜4095）の生 ADC 値で読める。
- その読み値が今使える状態かどうかを、ファームウェア自身の判定（valid tag）として読める。
- MQ チャネルの電圧を mV で読める（内部リファレンス電圧で校正済みの値）。
- NTC サーミスタの ADC 値・抵抗値（Ω）・電圧（mV）を読める。
- ヒータのモードと、間欠加熱の High / Low 時間を設定できる。
- インジケータ LED を on/off できる。I2C アドレスも変更できる（0x08〜0x77）。

できないこと・持っていないもの:

- **ガス濃度（ppm）は返らない。** 返るのは ADC 値と電圧だけである。ppm への換算式も、
  換算に必要な係数も、**ライブラリにもプロトコル PDF にも一切書かれていない**。
  製品ページが挙げる「300〜10,000 ppm」は MQ-5 素子そのものの検出範囲であって、
  このユニットが ppm を返すという意味ではない。
- **校正の手順が示されていない。** 清浄空気中の基準抵抗（いわゆる R0）を取る手順も、
  温湿度補正も、ライブラリには実装が無く、PDF にも記述が無い。**したがって、絶対値を
  求める用途にそのまま使える状態ではない。** 相対的な変化を見る用途が前提と考えるべき。
- **どのガスかは区別できない。** MQ-5 は可燃性ガスにまとめて反応する。出てくるのは
  1 本の ADC 値であって、ガスの種類の情報は無い。
- **温度レジスタは無い。** 摂氏の温度はライブラリがホスト側で計算している（後述）。
- 割り込み線は無い。**変化を知るにはポーリングするしかない。**
- ヒータの実温度は読めない。PDF は連続加熱時に素子の金属シェルが約 55 °C で安定すると
  書いているが、それを測るレジスタは無い。

## レジスタ

| アドレス | 長さ | R/W | 意味 |
|---|---|---|---|
| `0x00` | 1 | R/W | ヒータのモード。`0`=OFF（電源投入時の既定）、`1`=連続加熱、`2`=ピンレベル切り替え |
| `0x01` | 1 | R/W | インジケータ LED。`0`=off（電源投入時の既定）、`1`=on |
| `0x10` | 1 | R/W | 間欠加熱の High 時間。**単位は秒。30〜255（既定 30）。30 未満は無効** |
| `0x11` | 1 | R/W | 間欠加熱の Low 時間。**単位は秒。5〜255（既定 5）。5 未満は無効** |
| `0x20` | 1 | R | MQ センサの読み値（8bit ADC、0〜255）。**単位は無い。生の ADC 値である** |
| `0x30` | 2 | R | MQ センサの読み値（12bit ADC、0〜4095）。符号なし 16bit、**下位バイトが先**。単位は無い |
| `0x40` | 1 | R | MQ の読み値が有効かどうかのタグ（**極性は資料が食い違う。後述**） |
| `0x50` | 1 | R | NTC の読み値（8bit ADC、0〜255）。単位は無い |
| `0x60` | 2 | R | NTC の読み値（12bit ADC、0〜4095）。符号なし 16bit、下位バイトが先。単位は無い |
| `0x70` | 2 | R | NTC の抵抗値。符号なし 16bit、下位バイトが先。**単位は Ω** |
| `0x80` | 2 | R | 内部リファレンス電圧。符号なし 16bit、下位バイトが先。**単位は mV** |
| `0x82` | 2 | R | MQ チャネルの電圧。符号なし 16bit、下位バイトが先。**単位は mV** |
| `0x84` | 2 | R | NTC チャネルの電圧。符号なし 16bit、下位バイトが先。**単位は mV** |
| `0xFE` | 1 | R | ファームウェアのバージョン |
| `0xFF` | 1 | R/W | I2C アドレス（`0x08`〜`0x77`）。flash に書くので 20ms 以上かかる |

**バイト順**: PDF は 16bit の値をすべて `Value-L`, `Value-H` の順に並べ、
`ADC Value = (ADC Value-H << 8) | ADC Value-L` と式で書いている。つまり線上は
**下位バイトが先**。ライブラリも 2 バイトをそのまま `uint16_t` に memcpy していて、
対象がリトルエンディアンの ESP32 系ホストなので結果は一致する。

**単位の無い値と有る値を混ぜないこと**: `0x20` `0x30` `0x50` `0x60` は ADC のカウントで
**単位が無い**。物理量が付いているのは `0x70`（Ω）と `0x80` `0x82` `0x84`（mV）だけである。

**派生値であってレジスタではないもの**: 摂氏の温度。ライブラリの `getNTCTemperature()` は
`0x70` の抵抗値から、基準抵抗 10 kΩ・B 定数 3950 の Steinhart-Hart 形の式でホスト側で
計算している。**デバイスに温度レジスタは無い。**

**転送の形**: 書き込みは「ポインタバイト + ペイロード」を 1 トランザクションで送る。
読み出しはポインタバイトを書いて **repeated START**（`endTransmission(false)`）を打ち、
続けて必要な長さを要求する。

## 典型的な使い方

1. `0xFE` を読んでファームウェアのバージョンを確認する（疎通確認も兼ねる）。
2. **電源投入直後はヒータが OFF で、ガスの値は無効である。** まずモードを決める。
   - 連続加熱なら `0x00` に `1` を書く。
   - 間欠加熱なら、**先に** `0x10` と `0x11` に High / Low の秒数を書き、**そのあとで**
     `0x00` に `2` を書く。
3. **20 秒待つ。** 加熱開始から 20 秒間は読み値が安定しない。
4. 以後は周期的に `0x40`（valid tag）を読み、**有効になっていることを確かめてから**
   `0x20` / `0x30`（MQ の ADC）と `0x82`（MQ の電圧）を読む。付属サンプルもこの順で
   書かれている。
5. NTC 側（`0x60` `0x70` `0x84`）はヒータの状態に関係なくいつでも読める。温度が要るなら
   `0x70` を読んでホスト側で換算する。
6. 得られた値をどう解釈するかは、**このユニットの資料には書かれていない。** 清浄空気中の
   基準値を自分で取り、そこからの変化として扱うことになる。

## 利用上の注意

- **生の ADC 値は濃度ではない。** 「値が 1200 だからガスが何 ppm」とは言えない。
  MQ 系のセンサは素子ごとのばらつきが大きく、温度と湿度でも動く。このユニットの
  ライブラリと PDF は、**校正についても ppm への換算についても何も述べていない**。
  絶対値が要る用途では、別途の校正手順が必要になる。
- **暖機なしに読んだ値は無効である。** PDF は「During the first 20 s after heating
  starts, data readings are unstable」と明記している。間欠加熱モードでも同じで、
  High 期間に入ってから 20 秒経つまで有効にならない。つまり**High 時間を 30 秒未満に
  できないのは、20 秒の暖機が入るから**である。
- **`0x40`（valid tag）の極性が資料の中で矛盾している。** PDF の表の欄には
  「0: Valid 1: Invalid」と書かれているが、**同じ PDF の本文は逆のこと**を書いている
  （OFF モードでは「Valid tags is always 0」、加熱 20 秒後に「Valid tags becomes 1」）。
  ライブラリの enum も `VALID_TAG_INVALID = 0` / `VALID_TAG_VALID = 1` で、サンプルは
  `== 1` を有効として扱っている。**本ガイドは 1 = 有効の側を採るが、これは実測で
  確かめられていない。** 表の欄の記述は誤植と思われる。
- **間欠加熱の時間設定は、モードを入れる前に書く。** PDF は「must be set before
  enabling that mode; otherwise, it will not take effect」と明記している。順番を
  間違えると設定が反映されない。
- **短すぎる時間は黙って無視される。** High は 30 秒以上、Low は 5 秒以上。これより
  短い値を書いても「invalid」とされるだけで、エラーは返らない。
- **`0x10` と `0x11` は別々の 1 バイトレジスタだが、ライブラリは必ず 2 バイトまとめて
  読み書きする。** `setPulseTime()` は `0x10` に「High, Low」の 2 バイトを書き、
  `getPulseLevelTime()` も同じ形で読む。キャプチャに現れるのは 1 バイト転送 2 回では
  なく、`0x10` に対する 2 バイト転送 1 回である。
- **連続加熱は 190mA 近く食う。** OFF モードの 6.88mA に対し、連続加熱は 188.89mA
  （製品ページ）。バッテリ駆動でこのモードを入れっぱなしにすると、それだけで電源設計が
  変わる。間欠加熱モードがあるのはそのためである。
- **電圧は内部リファレンスで補正されている。** PDF いわく「The STM32 chip's reference
  voltage is not always a stable 3.3 V」。`0x82` `0x84` は `0x80` の内部リファレンス値で
  補正済みの実効電圧なので、ADC カウントから自前で電圧を出すなら `0x80` を使うこと。
  3.3V を定数として仮定しない。
- **LED は「有効なとき」しか光らない。** `0x01` を `1` にすると、valid tag が有効を
  示している間だけ点灯し、明るさは ADC 値に比例する。無効な間は消えたままなので、
  「LED が点かない」は暖機中というだけのことがある。
- **アドレス変更は即時反映。** `0xFF` に書くと新しいアドレスが flash に入り、すぐに
  効く。20ms 以上待ってから新アドレス宛に話しかける。書き換えた値を忘れると `0x11` を
  探しても見つからないユニットが手元に残る。復旧は scan で全アドレスを舐めることになる。
  flash なので頻繁に書き換えないこと。
- **本リポジトリの probe は read-only。** `scenarios/m5stack-mcu-u199/p0.yaml` は
  読めるレジスタを舐めるだけで、書き込みは `deferred` に置いてある。**probe の実行中は
  ヒータが OFF のままなので、`0x20` / `0x30` は「無効な状態の値」しか出てこない。**

## 出典と確度

- レジスタのアドレスと意味、16bit のバイト順と単位（Ω / mV）、20 秒の暖機、
  パルス時間の下限と既定値、モードを入れる前に時間を書くという順序、内部リファレンス
  電圧の位置づけ: ベンダーの Protocol PDF に記載がある。
- 転送長・アクセス方向、`0x10` を 2 バイトまとめて扱う実装、温度計算（10 kΩ / B=3950）:
  `M5Unit-MQ` ライブラリのソース（`collection/vendor/M5Unit-MQ` に commit `1d961cb` で
  固定）から起こした**推定**。`profiles/` の evidence は `inferred` / `tentative`。
- **食い違い（未確認）**: `0x40` の valid tag の極性。PDF の表は「0: Valid 1: Invalid」、
  PDF の本文とライブラリは「1 = 有効」。本ガイドは後者を採った。
- **資料に無いこと**: ppm への換算式、校正手順、R0 の取り方、温湿度補正。ライブラリにも
  PDF にも記述が無い。MQ 系センサ一般で言われる初回エージング（長時間の通電）についても
  **どちらの資料も何も述べていない**ので、本ガイドも述べない。
- **未確認**: 実機のキャプチャがまだ無い。レジスタが本当に表のとおり応答するか、
  暖機 20 秒の実挙動、valid tag の実際の遷移、400kHz で動くかは確かめていない。
- **未調査**: 書き込み側の挙動全般（モード、LED、パルス時間、アドレス変更）は
  probe が read-only のため触れていない。
