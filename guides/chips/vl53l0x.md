# VL53L0X — Time-of-Flight 測距センサ

> 940nm のレーザ（VCSEL）を出して、跳ね返ってくるまでの時間で距離を測るモジュール。
> 最大 2m。**ST はレジスタマップを公開していない。** 公開されているのは C の API
> （`VL53L0X_*`）であって、datasheet に載っているレジスタは疎通確認用の 5 本だけである。
> したがって `profiles/vl53l0x.yaml` のレジスタ表は、**サードパーティのドライバと ST の
> API ヘッダから起こした推定**である。
>
> **確度**: ST の datasheet **Rev 1（DocID029104、2016-05）**に基づく。ただし **ST 公式サイトの
> PDF は取得できず**、M5Stack がホストする同一文書のコピーを読んだ（版数・文書番号は同じ）。
> **実測は未着手**で、`profiles/vl53l0x.yaml` の evidence は `inferred` / `tentative`、
> `observations/vl53l0x/` はまだ無い。

## これは何か

4.4 × 2.4 × 1.0mm のパッケージに、940nm の VCSEL、そのドライバ、SPAD 受光素子、
そして専用のマイコンを収めた測距モジュール。**距離をミリメートル単位の数値として返す。**

「Time-of-Flight」なので、赤外光の**強さ**ではなく**往復時間**を測る。ここが赤外近接
センサとの決定的な差で、datasheet は「報告される距離は対象の反射率に依存しない」と
書いている（Features, p1）。反射率が変わると**測れる最大距離**は変わるが、測れている
間の値は正しい。

**できること**:

- 絶対距離を最大 2m まで測る（白 88% 反射・室内・33ms、Table 11, p26）。
- 測定時間（timing budget）を 20ms 〜 5 秒の範囲で選ぶ。長いほど精度と到達距離が上がる
  （§2.6.2, p15）。既定は 33ms（§2.10, p17）。
- 単発測定、連続測定、一定間隔の連続測定の 3 モード（API 経由、§2.4, p13）。
- 測定完了を GPIO1 の割り込みで受けるか、ポーリングで待つか選べる（§2.7, p15）。
- カバーガラス越しに使うための**クロストーク補正**を内蔵（要キャリブレーション、§2.3.3, p12）。
- オフセット補正、SPAD / 温度キャリブレーション。
- **I2C アドレスをソフトウェアで変更できる**（Features, p1）。同じバスに複数台を並べられる。

**できないこと・持っていないもの**:

- **2 次元の情報を返さない。** 視野（FOV）25° の中の「1 個の距離」だけである。物体の
  形も位置も分からない。ジェスチャ検出に使うなら、複数台を並べるか動きの時間変化から
  推定する。
- **複数の対象を分離できない。** FOV に 2 つの物体が入っていれば、返るのは 1 つの値。
  どちらの値かは条件次第。
- **屋外で性能が落ちる。** 太陽光の赤外がノイズになる。5kLux 相当の屋外曇天では
  白 88% の対象で 80cm、灰 17% で 50cm まで落ちる（Table 11, p26）。**直射日光下では
  さらに厳しい。**
- **レジスタマップが公開されていない。** datasheet が記述するのは電気的特性、タイミング、
  そして疎通確認用のレジスタだけ。**この文書だけを読んでドライバは書けない。**
  ST は API を使うことを前提にしている（§2.8, p15）。
- **最小測距距離が明記されていない。** オフセット補正は 10cm で行うことになっている
  （§5.3.1 の測定条件, p27）。極端に近い距離での挙動は文書からは分からない。
- **色や材質は分からない。** 返るのは距離と、測定が有効かどうかのステータスだけ。

**電気的な現実**:

- AVDD 2.6–3.5V（typ 2.8V）。**絶対最大 3.6V**（Table 6 / Table 7, p22）。
  **5V を直結すると壊れる。**
- **既定の I/O レベルは 1.8V である。** datasheet の注記がはっきり書いている —
  「API の既定モードは 1V8。2V8 モードは API がロードするデバイス設定で切り替えられる」
  （Table 7 注記 4, p22）。2V8 モードでは SDA / SCL / XSHUT / GPIO1 の High レベルを
  AVDD に合わせる（注記 3）。**モジュールを裸で使うときに最も事故が起きる箇所。**
- 電源投入順序の制約は無く、AVDD を掛ける前に I/O が High / Low / フローティングの
  どれでもよい（Table 7 注記 1, p22）。I/O は内部でフェイルセーフになっている。
- 消費電流は HW スタンバイ 3–7uA、SW スタンバイ 4–9uA、測定中は VCSEL 込みの平均値
  （Table 9, p23）。
- **XSHUT は常に駆動しなければならない。** 開放にするとリーク電流が流れる。ホスト側の
  状態が不定ならプルアップを付ける（§1.4 の注記, p8）。推奨 10kΩ。
- GPIO1 は**オープンドレイン**（Table 2, p7）。使わないなら未接続でよい。
- I2C のプルアップは AVDD 2.8V / 400kHz なら 1.5k〜2kΩ が推奨（§1.4 の注記, p8）。
- **Class 1 レーザ**（IEC 60825-1:2014 第 3 版準拠）。目に対して安全な等級だが、
  レーザには違いない。

## レジスタ・コマンド

### datasheet にレジスタ表が無い、という話

ST の立場は §2.8「Device programming and control」（p15）に書かれている —
「デバイスの物理制御インタフェースは I2C。デバイスを制御するためのソフトウェア層（API）が
提供される。API は VL53L0X API User Manual で説明される」。

そして §2.8 の前後には、API が「複雑な複数レジスタアクセスを意識せずにアプリケーションを
開発できるようにするターンキーソリューション」であること、「VL53L0X のファームウェアが
ハードウェアレジスタアクセスを全面的に管理する」ことが書かれている（p15）。

**つまりレジスタは意図的に隠されている。** datasheet が公開しているレジスタは
「ユーザの I2C インタフェースが正しく動いているかを検証するため」の 5 本だけである
（§3.2, p21）。

| アドレス | 値（フレッシュリセット後、API ロード前） |
|---|---|
| `0xC0` | `0xEE` |
| `0xC1` | `0xAA` |
| `0xC2` | `0x10` |
| `0x51` | `0x0099` |
| `0x61` | `0x0000` |

**これが datasheet に載っているレジスタのすべてである。**

### `profiles/vl53l0x.yaml` のレジスタ表はどこから来たか

`profiles/vl53l0x.yaml` の `coverage.features[0].note` が出どころを書いている —
「ST はレジスタマップの代わりに C API を公開している。凡例は Pololu / Adafruit の
ドライバと ST API のヘッダから」。

| アドレス | 名前 | 意味 | 根拠 |
|---|---|---|---|
| `0x00` | SYSRANGE_START | 測定開始。b0=1 で開始（`0x01` 単発 / `0x02`,`0x03` 連続） | ドライバ / API ヘッダ |
| `0x0B` | SYSTEM_INTERRUPT_CLEAR | `0x01` を書いて割り込みをクリア | ドライバ / API ヘッダ |
| `0x13` | RESULT_INTERRUPT_STATUS | 割り込みステータス（データ準備完了） | ドライバ / API ヘッダ |
| `0x14` | RESULT_RANGE_STATUS | 測定ステータス。**`0x1E` に 16bit の距離（mm）** | ドライバ / API ヘッダ |
| `0x8A` | I2C_SLAVE_DEVICE_ADDRESS | 現在の 7bit アドレス。書き換えでアドレス変更 | ドライバ / API ヘッダ |
| `0xC0` | IDENTIFICATION_MODEL_ID | `0xEE` を返す | **datasheet Table 4, p21 と一致** |
| `0xC2` | IDENTIFICATION_REVISION_ID | リセット後 `0x10` | **datasheet Table 4, p21 と一致** |

**`0xC0` と `0xC2` だけが datasheet で裏が取れている。** 残りは推定である。
ただし `0xC0`/`0xC2` が一致していることは、この推定の出どころ（ドライバ群）が
少なくともデタラメではないことの傍証にはなる。

### トランザクションの形（§3, p18-19）

datasheet が明記しているのはここまで:

```
書き込み: S | 0x52 | インデックス | データ | データ ... | P
読み出し: S | 0x52 | インデックス | Sr | 0x53 | データ | データ ... | P
```

- **インデックスは書き込みの 2 バイト目。** 最初のデータバイトを転送した後、
  **インデックスは自動的に +1 される**（§3, p19）。だから連続するレジスタへの
  読み書きはインデックスを毎回送り直さなくてよい。
- **マルチバイトは MSB first。** datasheet の注記が明示している —
  「I2C の read/write は 8, 16, 32bit のいずれでもよい。マルチバイトの read/write は
  常に昇順アドレスで MSB first」（§3.2 の Note と Table 5, p21）。
  **これは多くの I2C センサ（リトルエンディアン）と逆である。**

## 典型的な使い方

**ここから先は datasheet ではなく API / ドライバの世界である。**

datasheet が定めているのは電源投入と起動のところまで（§2.9.1, p16）:

1. AVDD を投入する。XSHUT をホストから制御する構成なら、XSHUT を Low に保つと
   HW スタンバイ（3–7uA）に入る。XSHUT を High にすると起動する。
2. XSHUT をホストが制御しない構成では、AVDD にプルアップしておく。この場合
   HW スタンバイを経ずに、ファームウェアブートの後そのまま SW スタンバイに入る。
3. **tBOOT は最大 1.2ms**（§2.9.1, p16）。この間 I2C を叩いてはいけない。
4. 起動が済んだら `0xC0` を読んで `0xEE` が返ることを確認する。これが datasheet で
   保証されている唯一の疎通確認である（Table 4, p21）。

その先（初期化 = tuning sequence、キャリブレーションデータのロード、測定の開始と
結果の取得）は API がやることで、**datasheet には手順が書かれていない。**
`profiles/` のレジスタを使った素朴な手順は以下のようになる**とされている**が、
これは推定であって確認されていない:

1. `0x00` に `0x01` を書いて単発測定を開始する。
2. `0x13` を読んで割り込みステータス（データ準備完了）を待つ。あるいは GPIO1 の
   割り込みを待つ。
3. `0x1E` から 16bit（**MSB first**）で距離を mm で読む。
4. `0x14` で測定ステータスを確認し、有効な測定かどうかを判定する。
5. `0x0B` に `0x01` を書いて割り込みをクリアする。
6. 次の測定へ。

**ST の API を使わない実装は、必ずどこかで「マジックナンバーの羅列」を含む。**
Pololu や Adafruit のドライバにある長い初期化シーケンスがそれで、**中身が何をして
いるかは公開されていない。**

## 利用上の注意

- **`0x29` は TCS34725 と同じアドレス。** この catalog で `0x29` を名乗るのは
  `vl53l0x`、`vl53l1x`、`tcs34725` の 3 つ。**Unit ToF と Unit Color を同じ I2C バスに
  直結すると必ず衝突する。** さらに **Unit ToF (U010) と Unit Mini ToF-90° (U196) は
  どちらも VL53L0X** なので、この 2 つを並べても衝突する。
  逃げ道:
  - **VL53L0X 側のアドレスを変える。** XSHUT で 1 台ずつ立ち上げ、起動したものから
    順にアドレスを振り直す。これが ST の想定する使い方（Features の
    "Programmable I2C address"）。**ただし XSHUT を制御できる配線が要る。**
  - TCA9548A のようなバススイッチで分ける。
  - TCS34725 のほうは**アドレスを変えられない**ので、動かすなら VL53L0X 側。
- **アドレス変更は電源を切ると戻る。** `0x8A` は揮発性で、リセットのたびに `0x29` に
  戻る。**起動のたびに振り直す必要がある。**（この挙動はドライバの実装から広く知られて
  いるが、**datasheet には記載が無い。**）
- **VL53L1X とは別物。** レジスタセットも API も違う（`chips/vl53l1x.yaml`）。
  `0x29` で ACK が返ったからといって、どちらが居るかは分からない。**`0xC0` を読んで
  `0xEE` が返れば VL53L0X**（VL53L1X の識別レジスタは別のアドレス）。
- **マルチバイトが MSB first。** リトルエンディアンを前提に書いたコードは距離が
  でたらめになる。16bit を読むとき、`0x1E` の直後のバイトが上位である。
- **既定の I/O レベルは 1.8V。** 3.3V のホストに直結すると、規定上は VIH を超えている。
  ブレイクアウトボードには通常レベルシフタか 2V8 モード設定が入っているが、
  **裸のモジュールを扱うときは Table 7 の注記 3 / 4（p22）を必ず読む。**
- **5V を掛けない。** 絶対最大 3.6V（Table 6, p22）。Grove の赤線は 5V。
- **XSHUT を開放にしない。** datasheet が「リーク電流を避けるため常に駆動すること」と
  明記している（§1.4 の注記, p8）。ホストの状態が不定ならプルアップ 10kΩ。
- **tBOOT の 1.2ms を待つ**（§2.9.1, p16）。電源投入直後の I2C は応答しない。
- **反射率と環境光で到達距離が大きく変わる。** 「2m」は白 88% の対象を室内で測った
  ときの typical 値であって、**灰色 17% の対象なら室内でも 80cm、屋外なら 50cm**
  （Table 11, p26）。仕様として 2m を当てにしてはいけない。
- **精度は距離に対する割合で規定されている。** 白 88% @120cm で標準偏差 4%（33ms）、
  灰 17% @70cm で 7%（Table 12, p27）。timing budget を 33ms から 66ms に伸ばすと
  数ポイント改善する。**精度が足りないときにまず触るのは timing budget。**
- **カバーガラスを付けるならクロストーク補正が要る**（§2.3.3, p12）。補正しないと、
  ガラス面からの反射が常に「近くに何かがある」として乗る。
- **400kHz は datasheet の上限。** ただし「400pF の負荷容量とプルアップの組み合わせでも
  制限される」と注記されている（Table 3 注記 1, p20）。
- **測定が失敗したときは距離ではなくエラーコードが返る。** 弱い信号、対象なし、などの
  ケースを IC 自身が判定している（§2.6.3, p15）。**ステータスを見ずに距離だけ読むと、
  意味の無い値を掴む。**

## 出典と確度

- **一次資料の入手について**: `chips/vl53l0x.yaml` は ST 公式の
  `st.com/resource/en/datasheet/vl53l0x.pdf` とベンダー（M5Stack）ホストの
  `VL53L0X_en.pdf` の 2 本を登録しているが、**ST 公式 URL からの取得は成立せず、
  実際に読んだのは M5Stack がホストするコピーのほう**である。両者は同じ文書
  （**Rev 1、DocID029104、2016-05**、全 40 ページ）で、`chips/vl53l0x.yaml` でも
  同じ版数・日付が記録されている。
- **datasheet から取れたこと（確度が高い）**: I2C アドレス `0x52`/`0x53`（= 7bit `0x29`）、
  最大 400kHz、インデックスの自動インクリメント、**マルチバイトが MSB first であること**、
  疎通確認用レジスタ 5 本の値、電源電圧と絶対最大定格、**既定 I/O レベルが 1.8V である
  こと**、XSHUT を駆動する必要があること、tBOOT 1.2ms、timing budget の範囲、
  測距距離と精度の実測表、FOV 25°。
- **datasheet に無いこと（= 推定であること）**: `0x00`（測定開始）、`0x0B`（割り込みクリア）、
  `0x13`（割り込みステータス）、`0x14` / `0x1E`（ステータスと距離）、`0x8A`（アドレス変更）。
  これらは Pololu / Adafruit のドライバと ST API のヘッダから起こしたもので、
  `profiles/vl53l0x.yaml` の evidence も `inferred` / `tentative`。
  **`0xC0` と `0xC2` だけは datasheet Table 4（p21）と一致している。**
- **datasheet に無いこと（その 2）**: 初期化シーケンス（tuning sequence）、
  キャリブレーションの具体的な手順、アドレス変更が揮発性であること、
  距離とステータスのビット割り当て。**ST は API User Manual 側でしか説明していない。**
  この catalog は API User Manual を取得していない。
- **未確認（実測なし）**: `0x29` が実際に ACK するか、`0xC0` が `0xEE` を返すか、
  `0xC2` が `0x10` を返すか、`0x8A` が `0x29` を返すか、400kHz で動くか。
  `observations/vl53l0x/` はまだ無い。
- **未調査**: `scenarios/vl53l0x/p0.yaml` では `tuning-sequence`、`single-ranging`、
  `continuous-ranging`、`address-reprogramming` がすべて deferred。
  **一度も距離を測っていない。**
- **本ガイドの「典型的な使い方」の後半（測定手順）は推定である。** datasheet が
  保証しているのは、電源投入から `0xC0` を読んで `0xEE` を確認するところまでである。
