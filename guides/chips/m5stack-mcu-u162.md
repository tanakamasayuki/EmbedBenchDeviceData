# Unit AIN4-20mA (U162) — 4-20mA 電流ループ入力ユニット

> 産業用センサの標準信号である 4-20mA の電流ループを絶縁して測り、I2C で読めるように
> したユニット。ホストから見えるのはユニット上の STM32G030 のファームウェアである。
>
> **⚠️ 相手は産業用の配線である。** ループには外部の 24V 電源が入ることがあり、現場の
> 配線は動力線と並走していることも多い。実験するときはループを外し、絶縁境界を跨ぐ配線を
> しないこと。本リポジトリの probe が read-only なのは、書き込みが校正を書き換えて
> バスを 500ms 止めるためでもある。
>
> **確度**: [`profiles/m5stack-mcu-u162.yaml`](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/profiles/m5stack-mcu-u162.yaml) の
> レジスタマップは `M5Module-4-20mA` ライブラリのソースから起こした推定
> （`evidence.source: inferred` / `confidence: tentative`）で、**実測では未確認**。
> **しかもこのライブラリは Unit（U162）と Module（4ch 版）を兼ねており、ベンダーの
> Unit 向け protocol PDF とはレジスタの意味が食い違う。**両方の主張を本文に併記した。

## これは何か

4-20mA 電流ループの受け側。センサが電流の大きさで値を伝えてくる方式（4mA が下限、
20mA が上限）を、200Ω のシャントで受けて、STM32G030F6P6 の ADC で測っている。
ループ側と I2C 側は **HCNR200 のリニアフォトカプラで絶縁**されている。

ループの配線は Grove ではなく **HT3.96-4P のねじ端子**に繋ぐ。センサが 2 線式（パッシブ）なら
外部の 24V 電源が必要で、4 線式（アクティブ）なら不要、というのがベンダーの説明である。

ホストから見えるのは STM32 であって、ADC でも絶縁アンプでもない。**つまり I2C の相手は
固定機能 IC ではなくファームウェアであり、レジスタマップはこの製品固有のもの**である。

用途は、圧力・液位・流量・温度など、4-20mA 出力の工業用センサを M5Stack 系のホストに繋ぐこと。

できること:

- 電流を、firmware が校正済みの 16bit 整数として読める。
- ADC の生の値も読める（診断用）。
- 既知の電流を流した状態で校正値を書き込み、firmware に再計算させられる。
- I2C アドレスを変更できる。

できないこと・持っていないもの:

- **割り込み線は無い。変化を知るにはポーリングするしかない。**
- **断線・レンジ外の通知が無い。** 4-20mA では 4mA 未満は「センサ異常または断線」を意味する
  約束だが、**そのことを知らせるフラグは無い**。値そのものを見て判断する。
- **校正値を読み返せない。** 校正レジスタは書き込み専用で、いま何を基準に換算しているかは
  分からない。校正をやり直す以外に確かめる手段が無い。
- **単位がどこにも明記されていない。**（後述。サンプルコードからの推定はある）
- ループ電源の供給機能は無い。パッシブセンサ用の 24V は外から用意する。
- 入力の帯域、平均化の有無、ADC の更新周期は資料に無い。

## レジスタ

**この製品ではライブラリと公式 PDF の主張が食い違う。** 先に食い違いを示す。

### ベンダーの Unit 向け protocol PDF（2023-01-30、firmware V1）

| アドレス | 長さ | R/W | 意味 |
|---|---|---|---|
| `0x00` | 2 | R | ADC の生値（16bit）。`ADC-L`, `ADC-H` → `ADC = ADC-L + ADC-H * 256`（**LSB first**） |
| `0x10` | 1 | R | 同じ ADC を 8bit で |
| `0x20` | 2 | R | 電流。`Current-L`, `Current-H` → `Current = Current-L + Current-H * 256`（**LSB first**） |
| `0xFE` | 1 | R | ファームウェアのバージョン |
| `0xFF` | 1 | R/W | I2C アドレス |

**PDF に載っているのはこの 5 行だけ**である。チャンネルは 1 つ、校正レジスタは無い。

### ライブラリ `M5Module-4-20mA`（profile はこちらを記録している）

| アドレス | 長さ | R/W | 意味 |
|---|---|---|---|
| `0x00` | 8 | R | 12bit ADC の生値を 4ch 分。ch *n* は `0x00 + n*2`、**2 バイト LSB first** |
| `0x20` | 8 | R | 校正後の電流を 4ch 分。ch *n* は `0x20 + n*2`、**2 バイト LSB first** |
| `0x30` | 8 | W | 校正点を 4ch 分。ch *n* は `0x30 + n*2`、**2 バイト LSB first**。**書くと firmware が換算式を作り直す** |
| `0xFE` | 1 | R | ファームウェアのバージョン |
| `0xFF` | 1 | R/W | I2C アドレス |

ライブラリは `if (channel > 3) return 0;` で読み出しを 4ch に制限している。これが 4ch という
数字の出どころで、**4ch なのは Module（AIN4-20mA Module 13.2）の方**である。

### どちらを信じるか

- `0x00` と `0x20` の**先頭 2 バイト（= ch0）については両者が一致する**。Unit を 1ch で使う限り、
  「`0x00` = ADC 生値 16bit LE、`0x20` = 電流 16bit LE」で読める。
- **`0x10` の意味が真っ向から食い違う。** PDF は「8bit の ADC 値」と言い、ライブラリは
  「12bit ADC ブロックの ch8 相当（実際には範囲外）」の位置として扱う。Unit で
  `getADC12BitsValue(ch)` に大きい ch を渡すと、PDF の言う 8bit ADC レジスタを読むことになる。
- **`0x30`（校正）は PDF に無い。** ライブラリ（2025 年時点のソース）にはあるが、
  Unit の firmware がこれを実装しているかは**未確認**。
- **ch1〜ch3 は Unit には存在しない。** ベンダーの Unit 用サンプルも ch0 しか読んでいない
  （Module 用サンプルだけが 0〜3 を回している）。

### 単位

**どちらの資料も電流レジスタの単位を書いていない。** ライブラリの API も生の 16bit を返すだけで
係数を掛けない。手がかりはサンプルコードだけで、そこでは

```
(float)(meter.getCurrentValue(0)) / 100.0   // "%.2fmA" と表示
```

としている。つまり **1 LSB = 0.01mA（= 10µA）** という読みになる。4-20mA なら生値は
400〜2000 の範囲に入る計算で、桁としても矛盾しない。ただし**これはサンプルコードからの
推定であって、仕様として明記された値ではない**。

`0x30` に書く校正値も、同じスケールで与えるのが自然だが、これも明記は無い。

**転送の形**: 書き込みは「ポインタバイト + ペイロード」を 1 トランザクションで送る。
読み出しはポインタバイトを書いて **repeated START**（`endTransmission(false)`）を打ち、続けて
必要な長さを要求する。ただし `getFirmwareVersion()` と `getI2CAddress()` の 2 つだけは
repeated START ではなく STOP を挟む。

## 典型的な使い方

1. `0xFE` を読んでファームウェアのバージョンを確認する（通信確認も兼ねる）。
2. ループを繋ぐ。パッシブセンサなら外部 24V を入れる。
3. `0x20` を 2 バイト読み、リトルエンディアンの 16bit として組み立て、100 で割って mA にする。
4. 値がおかしいときは `0x00`（ADC の生値）も読んで、ADC 段で既に変なのか、換算だけが
   変なのかを切り分ける。
5. 校正が必要なら、**基準器で確かめた既知の電流を流した状態で** `0x30` に「いま流れている
   電流の値」を書く。書いたあと firmware は 500ms 応答できない（後述）。

## 利用上の注意

### 安全

- **ループ側には外部 24V が入り得る。** パッシブセンサの構成では 24V DC 電源をループに
  直列に入れる。実験のためにユニット単体を触るときは、ループを外してからにする。
- **絶縁境界を跨がない。** ループ側（HT3.96-4P 端子）と I2C 側（Grove）は HCNR200 で
  分離されている。GND を共通にする、テスタのクリップで橋渡しする、といった配線は
  この絶縁を無効にする。
- **`0x30` への書き込みは校正の破壊的な変更である。** 一度書くと、それ以前の換算は失われる。
  何が入っていたかを読み返す手段は無い。
- **本リポジトリの probe（`scenarios/m5stack-mcu-u162/p0.yaml`）は `safety: read-only`。**
  `0x30` とアドレス変更には一切触れない。

### プロトコル

- **校正の書き込みはバスを 500ms 止める。** `setCalCurrent()` は書き込み後に `delay(500)` を
  入れている。これはライブラリの都合ではなく、**firmware がその間応答できない（おそらく
  フラッシュ書き込み中）ことの表明**とみるべきである。この 500ms の間にバスへ何かを出すと
  NAK される可能性が高い。同じバスに他のデバイスがぶら下がっているなら、その分の
  停止も見込んでおく。
- **校正のチャンネル番号にガードが無い。** 読み出し 2 つには `if (channel > 3) return 0;` が
  あるのに、`setCalCurrent()` には無い。大きい `channel` を渡すと `0x30 + channel*2` を
  そのまま書き、**ブロックの外へ書き込む**。`channel = 8` なら `0x40`、`channel = 103` なら
  `0xFE`（= ファームウェアバージョン）に届く（オフセットが偶数なので `0xFF` そのものには
  当たらないが、それは偶然でしかない）。Unit では ch は 0 だけを使うこと。
- **`0x00` と `0x20` は同じ測定の 2 つの見え方。** `0x00` は変換器の生の出力、`0x20` は
  firmware が校正を適用したあとの値。電流が欲しいなら `0x20`、切り分けが必要なときだけ `0x00`。
- **16bit 値はすべて LSB first。**
- **単位はサンプルコード由来の推定である。** 0.01mA/LSB を前提にした表示を「仕様」として
  ドキュメントに書かない。手元の基準器で 1 点確かめるのが確実である。
- **断線・レンジ外は自分で判定する。** 4mA を大きく下回る値（生値 400 未満）が続いたら
  ループの異常を疑う、といった判定はホスト側の仕事。デバイスは何も言わない。
- **アドレス変更は即時反映。** `0xFF` に書いた次のトランザクションはもう新アドレス宛に
  出さないと応答しない。復旧は scan で全アドレスを舐めることになる。
- **ライブラリのバグ: I2C 速度が化ける。** `MODULE_4_20MA` のメンバは `uint8_t _speed;` なのに、
  `begin()` は `uint32_t speed = 100000L` を受け取ってそこへ代入する。100000 は 8bit に
  切り詰められて **160** になり、その値がそのまま `Wire.begin(sda, scl, 160)` に渡る。
  つまり既定の呼び方（ベンダーのサンプルを含む）をすると、**バスが 100kHz ではなく 160Hz に
  設定される**。ホスト側で改めて `Wire.setClock()` を呼ぶか、ライブラリを直すこと。
- **ライブラリのバグ: 一部のメソッドがグローバルの `Wire` から読む。**
  `getFirmwareVersion()` と `getI2CAddress()` は書き込みを `_wire` で行うのに、読み出しだけ
  `Wire.read()`（グローバル）を使っている。`begin()` に `Wire1` を渡した構成では、
  この 2 つだけ別のバスから読もうとして壊れる。
- **ライブラリ名が示すとおり、これは本来 Module 用のライブラリである。** Unit で使うときは
  ch0 以外を触らない。`examples/UnitAIN4-20mA/` が Unit 用、`examples/ModuleAIN4-20mA/` が
  Module 用のサンプルで、前者は ch0 しか読んでいない。

## 出典と確度

- profile が記録しているレジスタマップ（4ch のバンク構成、`0x30` の校正、500ms の待ち）:
  `M5Module-4-20mA` ライブラリのソース（`collection/vendor/M5Module-4-20mA` に commit 固定で取得）。
- Unit 単体としてのレジスタマップ（1ch、`0x10` = 8bit ADC、校正レジスタ無し）:
  ベンダーの Unit AIN4-20mA I2C Protocol PDF（V1、2023-01-30）。**profile とこの PDF は
  食い違っており、どちらが手元の firmware の実態かは実測でしか決まらない。**
- 単位 0.01mA/LSB: ベンダーの Unit 用サンプルコードが `/100.0` して `mA` と表示していることからの
  **推定**。ライブラリの API にも PDF にも単位の記述は無い。
- 絶縁（HCNR200）、入力インピーダンス 200Ω、24V 外部電源、端子形状: 製品ページの仕様表。
- 転送長・アクセス方向・バイト順: ライブラリのメソッド本体から起こした**推定**。
- **PDF 側の誤り**: PDF の表は Firmware Version と I2C Address の両方を `0xF0` と書いている。
  1 つのアドレスに 2 つのレジスタは置けない。ライブラリの `0xFE` / `0xFF` が正しいとみて
  本文はそちらを採った（M5Stack の他ユニットの protocol PDF にも同じ誤植がある）。
- **未確認**: 実機のキャプチャがまだ無い。`0x10` がどちらの意味なのか、`0x30` が Unit の
  firmware に存在するのか、ch1〜3 のアドレスに何が返るのか、単位が本当に 0.01mA なのか、
  400kHz で動くかは確かめられていない。
- **未調査**: 校正の書き込みとアドレス変更は probe が read-only のため触れていない。
  これは意図的な制限であり、校正の書き込みが不可逆だからである。
