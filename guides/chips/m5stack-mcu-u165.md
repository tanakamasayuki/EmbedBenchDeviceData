# Unit 8Servos (U165) — 8 チャンネルのサーボ / 汎用 IO ドライバ

> サーボ 8 個ぶんの PWM と、汎用 IO・ADC・NeoPixel・PWM を I2C 1 本から扱えるようにした
> ドライバ。チャンネルごとに「何として使うか」を先に宣言してから叩く構造になっている。
>
> **確度**: M5Stack が Unit 8Servo I2C Protocol という PDF（2023-03-24、firmware V1 向け）を
> 公開しており、レジスタ表はそこと `M5Unit-8Servo` ライブラリのソースの両方に存在する。
> 本文の転送長・バイト順・アクセス方向は**ライブラリのソースから起こした推定**で、
> 実測では未確認。
>
> **安全**: このユニットは書き込むと**その場でサーボが動く**。`0x50` / `0x60` に書けば軸が回り、
> `0x10` に書けば出力ピンが駆動される。本リポジトリの probe が read-only なのは
> まさにこのためで（[docs/VERIFY.ja.md](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/docs/VERIFY.ja.md) の「アクチュエータを持つユニット」）、
> 書き込み側の挙動は一切確かめていない。

## これは何か

STM32F030F4P6 に M5Stack のファームウェアを載せ、8 本の IO を束ねたユニット。ホストから
見える I2C の相手は STM32 であって、サーボでも LED でもない。**つまり固定機能 IC ではなく
ファームウェアであり、レジスタマップはこの製品固有のもの**である。

物理的には Grove（HY2.0-4P）で I2C とロジック電源をもらい、HT3.96-4P の端子台からサーボ用の
電源（9〜24V または 5V の 2 系統）を入れる。サーボ用の出力は 8 チャンネル合計で DC 5V@3A まで。
基板上には電流検出アンプ INA199A1DCKR と、主電源の MOS スイッチ回路が載っている。

できること:

- **チャンネルごとに役割を選べる。** `0x00+ch` に 1 バイト書いて、デジタル入力 / デジタル出力 /
  ADC 入力 / サーボ / NeoPixel(RGB LED) / PWM のどれとして使うかを決める。
- サーボは**角度**（0〜180 度）でも**パルス幅**（500〜2500 µs）でも指令できる。
- デジタル出力の H/L、デジタル入力の読み出し。
- ADC を 8bit（0〜255）と 12bit（0〜4095）の 2 通りで読める。
- PWM は duty 0〜100、周波数 1kHz。
- NeoPixel をチャンネルごとに RGB で光らせられる。
- サーボ電源の**合計**電流を float で読める。
- I2C アドレスを変更できる。

できないこと・持っていないもの:

- **サーボの実際の位置は読めない。** `0x50` / `0x60` は指令値であって現在角ではない。
  一般的なホビーサーボは位置を返さないので、これはユニットの制限ではなく構成上の制限。
- **電流はユニット全体で 1 個だけ。** チャンネル別の電流は取れないので、どのサーボが
  引っかかっているかは電流からは分からない。
- **割り込み線が無い。** 入力の変化を知るにはポーリングするしかない。
- **PWM の周波数は変えられない**（vendor PDF に 1kHz と書いてある固定値）。サーボのフレーム
  周期を変えるレジスタも無い。
- 製品ページにある「主電源 MOS によるサーボの release/lock」に対応するレジスタは、
  vendor PDF にもライブラリにも見当たらない。どう叩くのかは**未確認**。
- ADC の基準電圧・入力レンジはどの資料にも書かれていない。読めるのは**生のカウントだけ**で、
  電圧に直す係数は**未確認**。
- 8bit ADC と 12bit ADC が同じ入力の別表現なのかどうかも、資料には明記が無い。

## 早見表

| 項目 | 値 |
|---|---|
| I2C アドレス | `0x25`（既定） |
| アドレス変更 | レジスタ `0xFF` に書き込み（値の範囲 0〜127）。**書いた直後から新アドレスで応答する** |
| 電源 | ロジックは Grove の 5V。サーボ電源は HT3.96-4P から 9〜24V / 5V の 2 系統。8ch 合計 DC 5V@3A |
| インタフェース | Grove HY2.0-4P（I2C）+ HT3.96-4P（サーボ / 電源） |
| I2C 速度 | ライブラリは速度を指定しない（`Wire.begin(sda, scl)` のみ）。上限は firmware 依存で**未実測** |
| 中身 | STM32F030F4P6 + INA199A1DCKR（電流検出） |
| 割り込み | 無し（ポーリング） |
| バイト順 | 数値はリトルエンディアン（LSB first）。RGB だけは R, G, B の順で数値ではない |
| チャンネル数 | 8（IO0〜IO7） |

## レジスタ

**すべての機能ブロックが「ベースアドレス + チャンネル番号 × ストライド」の 8 個並び**になって
いる。下表の「長さ」はブロック全体、「1ch」がストライド。チャンネル n を叩くアドレスは
ベース + n × ストライド。

| ベース | 長さ | 1ch | R/W | 意味 |
|---|---|---|---|---|
| `0x00` | 8 | 1 | W (PDF は W/R) | チャンネルのモード。`0`=デジタル入力, `1`=デジタル出力, `2`=ADC, `3`=サーボ, `4`=NeoPixel, `5`=PWM |
| `0x10` | 8 | 1 | W | デジタル出力レベル。`0`=LOW, `1`=HIGH |
| `0x20` | 8 | 1 | R | デジタル入力レベル。`0`=LOW, `1`=HIGH |
| `0x30` | 8 | 1 | R | 8bit ADC。0〜255 の生カウント（単位の記載なし） |
| `0x40` | 16 | 2 | R | 12bit ADC。0〜4095、**符号なし 16bit・LSB first** |
| `0x50` | 8 | 1 | W (PDF は W/R) | サーボ角度。**単位は度**、0〜180 |
| `0x60` | 16 | 2 | W (PDF は W/R) | サーボパルス幅。**単位は µs**、書き込みは 500〜2500、**符号なし 16bit・LSB first**。読み返すと 10 倍の値（下記注意） |
| `0x70` | 24 | 3 | W (PDF は W/R) | NeoPixel の色。**R, G, B の順**（数値ではなくバイト列）。`0x70`〜`0x87` を占める |
| `0x90` | 8 | 1 | W (PDF は W/R) | PWM デューティ。**0〜100**（％）、周波数 1kHz。読み返すと 10 倍の値（下記注意） |
| `0xA0` | 4 | — | R | サーボ電源の合計電流。**IEEE 754 単精度 float・リトルエンディアン**。vendor PDF は "float" とだけ書き、**単位を書いていない**（profile は A と記録しているが未確認） |
| `0xFD` | 1 | — | W | `1` を書くとファーム更新用ブートローダに入る |
| `0xFE` | 1 | — | R | ファームウェアのバージョン |
| `0xFF` | 1 | — | R/W | I2C アドレス（0〜127、既定 `0x25`） |

**転送の形**: 書き込みは「ポインタバイト + ペイロード」を 1 トランザクションで送る。読み出しは
ポインタバイトを書いて **repeated START**（`endTransmission(false)`）を打ち、続けて必要な長さを
要求する。ただし `getFirmwareVersion()` と `getI2CAddress()` だけは repeated START ではなく
STOP を打ってから読んでいるので、firmware は両方の組み立て方を受けるらしい。

**アクセス方向について**: ライブラリはモード・出力・サーボ・RGB・PWM の各バンクを**一度も
読み返さない**ので、profile では write-only として記録している。一方 vendor PDF は同じ
レジスタを W/R と書いている。**読めるかどうかは未確認**で、読める前提で設計しないほうがよい。

## 典型的な使い方

1. `0xFE` を読んでファームウェアのバージョンを確認する（通信が成立しているかの確認も兼ねる）。
2. **使うチャンネルのモードを先に書く。** サーボなら `0x00+ch` に `3`。ここを飛ばすと、
   あとで `0x50` に角度を書いても何も起きない。ライブラリの `begin()` はモードを一切設定しない。
3. サーボを動かすなら `0x50+ch` に角度（度）、細かく指定したければ `0x60+ch*2` にパルス幅（µs、LSB first）。
4. ADC を読むなら `0x00+ch` に `2` を書いてから `0x30+ch`（8bit）または `0x40+ch*2`（12bit、LSB first）。
5. NeoPixel なら `0x00+ch` に `4` を書いてから `0x70+ch*3` に `{R, G, B}` の 3 バイト。
6. 消費電流を見るなら `0xA0` から 4 バイト読み、リトルエンディアンの float として解釈する。

## 利用上の注意

- **モードを書かないと何も動かない。** レジスタ表には表れない順序制約で、`0x00+ch` が
  対応するモードになって初めて、そのチャンネルのバンクが意味を持つ。ライブラリの `begin()` は
  存在確認しかしないので、モード設定はアプリ側の責任。
- **サーボパルスの読み返しは書いた値の 10 倍。** vendor PDF の脚注に明記されている
  （write 500 → read 5000、10 で割れ）。ライブラリはこの補正を**していない**。もっとも
  ライブラリには `0x60` の getter が無いので、自前で読む driver を書いたときに初めて刺さる。
- **PWM デューティの読み返しも 10 倍。** 同じく PDF の脚注（write 10 → read 100）。
  こちらもライブラリに getter が無い。
- **PWM デューティは 0〜100 であって 0〜255 ではない。** ライブラリの `setPWM(uint8_t pin,
  uint8_t angle)` は第 2 引数の名前が `angle` になっているが、これは duty である。
- **`0xA0` の単位が資料に無い。** PDF は "float" とだけ書いている。profile はアンペアと
  記録しているが、これは**推定**であって確認されていない。実測で桁を確かめるまで、
  表示に単位を付けないほうが安全。
- **RGB バンクは `0x70`〜`0x87` の 24 バイト。** 次のブロックが `0x90` から始まるのはこのため。
  ch7 の RGB は `0x85`〜`0x87` なので、ここで 3 バイトを超えて書くとバンクの外に出る。
- **RGB は数値ではない。** `uint32_t` の色を渡すライブラリ API に引きずられて 24bit 整数だと
  思うと順序を間違える。バス上は R, G, B の順の 3 バイトである。
- **ライブラリの既知の不具合**:
  - `setAllPinMode()` は 8 バイトを 1 ブロックで `0x00` に書いたあと `return` しており、
    その後ろのチャンネル毎ループは**到達しない**。実際に出るのはブロック書き込みだけ。
  - `setOnePinMode(pin, mode)` は**レジスタ番号 `pin` に**書いている。モードバンクが
    `0x00` から始まるから結果的に正しいだけで、ベースアドレスを足していない。
  - `getServoCurrent()` は `readBytes()` の戻り値を見ない。読み出しが失敗すると
    **未初期化の float** がそのまま返る。
  - `getI2CAddress()` と `getFirmwareVersion()` は `_wire->read()` ではなく
    グローバルの `Wire.read()` を呼んでいる。`Wire1` を渡していると別のバスから読む。
  - ヘッダの `M5_UNIT_8SERVO_FW_VERSION_REG` / `M5_UNIT_8SERVO_ADDRESS_REG` は
    `FIRMWARE_VERSION_REG` / `I2C_ADDRESS_REG` と同じ値の重複定義。**レジスタは 4 個ではなく 2 個**。
- **アドレス変更は即時反映。** `0xFF` に書いた次のトランザクションはもう新アドレス宛に出さないと
  応答しない。書き換えた値を忘れると `0x25` を探しても見つからないユニットが手元に残る。
- **`0xFD` に書くとブートローダに入る。** 通常のアプリケーションから触る理由は無い。
- **モードの値域が資料内で食い違う。** PDF の表の注記は "Mode:0~4" だが、同じ PDF の脚注は
  0〜5 の 6 種類を列挙しており、ライブラリの enum も 6 個ある。どちらが正しいかは firmware 依存で**未確認**。
- **実験するときは可動部を外す。** サーボのホーンに何も付けず、リンケージを外し、腕が自由に
  振れる状態にしてから書き込むこと。角度指令は途中経過を持たず、書いた瞬間に全速で動く。

## 出典と確度

- レジスタのアドレスと意味: `M5Unit-8Servo` ライブラリのソース（`collection/vendor/M5Unit-8Servo` に
  commit 固定で取得）。ベンダーの Protocol PDF とも整合する。
- 単位（度 / µs / % / 生カウント）、値域、×10 の読み返し規則: ベンダー Protocol PDF。
- 転送長・アクセス方向・バイト順: 同ライブラリのメソッド本体から起こした**推定**。
- **未確認**: 実機のキャプチャがまだ無い（`observations/m5stack-mcu-u165/` は存在しない）。
  レジスタが表のとおり応答するか、モード / サーボ / RGB / PWM の各バンクが本当に読めるか、
  400kHz で動くかは確かめられていない。
- **未確認**: `0xA0` の単位。PDF は型（float）しか書いていない。
- **未確認**: 主電源 MOS スイッチ（release/lock）の制御方法。どの資料にもレジスタが無い。
- **未調査**: 書き込み側の挙動全般。probe が read-only なので、モード設定・サーボ・出力・
  RGB・アドレス変更のいずれも実機では触っていない。
