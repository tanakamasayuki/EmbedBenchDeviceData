# Unit QRCode (U173) — QR / バーコードスキャナユニット

> カメラで QR コードやバーコードを読み、**デコード済みの文字列だけ**を I2C から渡してくる
> スキャナ。ホストは「読めたか」を聞き、「何バイトか」を聞き、その長さぶんを吸い出す。
>
> **確度**: M5Stack が Unit QRCode I2C Protocol という PDF（2024-01-02、PDF 自身の表記は
> firmware **V3** 向け。catalog の note は V1 と書いており食い違う）を公開しており、レジスタ表は
> そこと `M5Unit-QRCode` ライブラリのソースの両方に存在する。本文の転送長・バイト順・
> アクセス方向は**ライブラリのソースから起こした推定**で、実測では未確認。

## これは何か

640×480 の CMOS センサと M14 レンズ、白色の照明 LED、赤色の照準 LED、ブザー、トリガ
ボタンを、STM32F030F4P6 に載せた M5Stack ファームウェアが束ねているユニット。ホストから
見える I2C の相手は STM32 であって、カメラでもデコーダでもない。**つまり固定機能 IC ではなく
ファームウェアであり、レジスタマップはこの製品固有のもの**である。

側面のトグルスイッチで **I2C と UART を切り替える**。UART 側は完全に別のプロトコル
（同じライブラリの `M5UnitQRCodeUART.cpp`）で、このガイドは I2C 側だけを扱う。

読める種類は 2 次元が 3 種（PDF417 / QR Code / Data Matrix）、1 次元が 14 種
（Code128, EAN-13, UPC-A, Codabar など）。

できること:

- **自動トリガ**（電源投入時の既定。常時スキャンし続ける）と**手動トリガ**（言われたときだけ
  スキャンする）を切り替えられる。
- 手動モードで、スキャンの開始 / 停止を指示できる。
- デコード完了フラグ、ペイロード長、ペイロード本体を読める。
- 本体のトリガボタンが押されているかを読める。
- I2C アドレスを変更できる。

できないこと・持っていないもの:

- **どのシンボル体系を有効にするかを I2C からは設定できない。** マップにレジスタが無い。
- **読めたコードの種類が分からない。** 返ってくるのはペイロードのバイト列だけで、
  「QR だったか EAN だったか」を示すレジスタは無い。
- **照明 LED・照準 LED・ブザーを I2C から制御できない。** ファームウェアが勝手に鳴らし、光らせる。
- **画像は取れない。** デコード結果だけ。
- **割り込み線が無い。** 読めたことを知るには `0x0010` をポーリングするしかない。
- UART / I2C の切り替えは物理スイッチで、レジスタからは変えられない。
- ペイロードのアドレス範囲は vendor PDF によれば `0x1000`〜`0x11FF`、つまり**最大 512 バイト**。

## レジスタ

**このユニットだけレジスタポインタが 2 バイト**で、しかも下位バイトが先に出る。すべての転送は
`[reg & 0xFF][reg >> 8]` で始まる。

| アドレス | 長さ | R/W | 意味 |
|---|---|---|---|
| `0x0000` | 1 | W | スキャンの開始 / 停止。`1`=連続デコード開始、`0`=停止。**手動トリガモードでのみ有効** |
| `0x0010` | 1 | R (PDF は R/W) | デコード状態。`0`=未完了、`1`=データあり、`2`=読み直しが必要。**ペイロードを読むか `0` を書くとクリアされる**（PDF 記載） |
| `0x0020` | 2 | R | ペイロードのバイト数。**符号なし 16bit・LSB first**（Length-L, Length-H） |
| `0x0030` | 1 | R/W | トリガモード。`0`=自動（既定、常時スキャン）、`1`=手動 |
| `0x0040` | 1 | R | トリガボタンの状態。**`0`=押下、`1`=非押下（アクティブ Low）** |
| `0x00FD` | 1 | W | `1` を書くとファーム更新用ブートローダに入る |
| `0x00FE` | 1 | R | ファームウェアのバージョン |
| `0x00FF` | 1 | R/W | I2C アドレス |
| `0x1000` | 可変 | R | デコード済みペイロード。長さは `0x0020` の値。PDF によれば領域は `0x1000`〜`0x11FF`（最大 512 バイト） |

ポインタが 2 バイトなので、マップは「`0x0000`〜`0x00FF` の制御ページ」と「`0x1000` のデータ
ページ」に分かれる。他の M5Stack ユニットと同じ `0xFD` / `0xFE` / `0xFF` は、上位バイトを 0 に
した `0x00FD` / `0x00FE` / `0x00FF` として同じ位置に居る。

**転送の形**: 書き込みは `[reg_lo][reg_hi][data...]` を 1 トランザクションで。読み出しは
`[reg_lo][reg_hi]` を書いて **repeated START** を打ち、続けて必要な長さを要求する。ただし
`getFirmwareVersion()` / `getI2CAddress()` / `setI2CAddress()` は同じ 2 バイトを手で組み立てて
STOP を打っているので、firmware は両方の組み立て方を受けるらしい。

## 典型的な使い方

1. `0x00FE` を読んでファームウェアのバージョンを確認する（通信確認も兼ねる）。
2. 常時読ませるなら `0x0030` に `0`（自動）。押したときだけ読ませるなら `1`（手動）にして、
   読ませたい瞬間に `0x0000` に `1` を書く。止めるときは `0x0000` に `0`。
3. `0x0010` をポーリングする。`1` になったらデータあり。`2` は「読み直しが必要」。
4. `0x0020` から 2 バイト（LSB first）読んで、ペイロード長を得る。
5. **その長さちょうどを** `0x1000` からバースト読みする。
6. 読み終わるとフラグはクリアされる（PDF 記載、実測は未確認）。次のコードを待つなら 3 に戻る。

## 利用上の注意

- **ポインタが 2 バイトであることを忘れない。** 他の M5Stack ユニットのつもりで 1 バイトの
  ポインタを書くと、firmware は 2 バイト目を待つか、次に来たデータバイトを上位バイトと
  解釈する。汎用の I2C ツールで叩くときに最初に嵌まる。
- **トリガボタンはアクティブ Low。** `0x0040` が `0` のときが押下。ライブラリは生の値を
  そのまま返すので、素直に真偽値に変換すると意味が逆になる。
- **`0x0010` は 3 値であって真偽値ではない。** `2`（読み直しが必要）を「データあり」と
  同一視すると、壊れたペイロードを掴む。ライブラリは値をそのまま返すだけで解釈しない。
- **読む長さは `0x0020` の値ちょうどにする。** `getDecodeData(uint8_t *data, uint16_t len)` は
  長さを引数で受け取るだけで、バッファ長も宣言長も検査しない。呼び出し側の規律だけが
  読み過ぎ・書き過ぎを止めている。
- **ペイロードは Arduino の Wire バッファに収まらないことがある。** 領域は最大 512 バイト
  あるのに、`requestFrom()` 一発で取れる長さはホスト側の I2C バッファ（ESP32 系の既定は
  128 バイト、AVR は 32 バイト）で頭打ちになる。ライブラリは `requestFrom()` の戻り値を
  見ずに `read()` を回すので、足りない分は `-1`（= `0xFF`）が詰まる。長いペイロードを扱うなら
  分割読み出しを自分で書く必要がある。**分割読み出しが `0x1000+n` のようなオフセット指定で
  できるかどうかは未確認。**
- **手動モードで `0x0000` に `1` を書き忘れると、いつまでもデータが来ない。** 自動モードなら
  不要。モードを取り違えたときの症状が「無反応」なので原因が分かりにくい。
- **ライブラリの既知の不具合**: `M5UnitQRCodeI2C.h` のメンバ `_speed` が `uint8_t` なのに、
  `begin()` の引数は `uint32_t speed = 100000L`。代入で下位 1 バイトに切り詰められ、既定では
  `100000 & 0xFF = 160` が `Wire.begin(sda, scl, 160)` に渡る。**要求した I2C クロックは
  そのまま届かない。** どんな値を渡しても下位 8bit しか残らないので、`begin()` 経由で
  まともなクロックを指定する手段が無い。実際に 160Hz で動くのか、ドライバ側が弾いて
  既定値のままになるのかは**未確認**。速度を決めたいなら `begin()` の後に自分で
  `Wire.setClock()` を呼ぶこと。
- **`getI2CAddress()` と `getFirmwareVersion()` はグローバルの `Wire.read()` を呼んでいる。**
  `Wire1` を渡していると別のバスから読む。
- **アドレス変更は即時反映。** `0x00FF` に書いた次のトランザクションはもう新アドレス宛に
  出さないと応答しない。
- **`0x00FD` に書くとブートローダに入る。** 通常のアプリケーションから触る理由は無い。
- ライブラリはフラグを明示的にクリアする API を持たない。クリア規則は vendor PDF にしか
  書かれておらず、**実測では確かめていない**。

## 出典と確度

- レジスタのアドレスと意味: `M5Unit-QRCode` ライブラリのソース（`collection/vendor/M5Unit-QRCode` に
  commit 固定で取得）。ベンダーの Protocol PDF とも整合する。
- ボタンの極性（`0`=押下）、`0x0010` の 3 値とクリア規則、データ領域が `0x1000`〜`0x11FF` で
  あること: ベンダー Protocol PDF のみが出典。**実測では未確認。**
- 2 バイトポインタ・転送長・アクセス方向・バイト順: 同ライブラリのメソッド本体から起こした**推定**。
- **未確認**: 実機のキャプチャがまだ無い（`observations/m5stack-mcu-u173/` は存在しない）。
  ペイロードの分割読み出しができるか、フラグが本当に読み出しでクリアされるか、
  400kHz で動くかは確かめられていない。
- **注記**: `chips/m5stack-mcu-u173.yaml` は datasheet の note に "firmware version V1" と
  書いているが、PDF 自身の表紙は V3（2024/1/2）である。どちらの版の firmware が手元の
  ユニットに載っているかは `0x00FE` を読んで確かめるしかない。
- **未調査**: 書き込み側の挙動全般（トリガ、モード変更、アドレス変更）は probe が
  read-only のため触れていない。
