# Unit 16-Key Capacitive Touch / Unit Makey (U026) — 16 接点タッチ入力ユニット

> 導電物（果物など）を触ると鳴る Makey Makey 風の入力ユニット。**レジスタは存在しない。**
> ポインタバイト無しでバイトを読むと、16 個の接点の押下状態がビットとして返る。
>
> **確度**: datasheet も I2C プロトコル文書も専用 Arduino ライブラリも無い。本リポジトリに
> `profiles/m5stack-mcu-u026.yaml` は存在せず、実測も持っていない。ただし本機は
> **ベンダーがスレーブ側 firmware のソースを公開している**ため、6 機種の中では
> ビット配置の根拠が最も強い。それでも**バス上で確認された挙動は一つも無く**、
> しかもその公開ソースは後述のとおり複数の点で実機と食い違っている疑いがある。

## これは何か

16 個のタッチ接点（クリップで導電物を挟んで使う）と、ブザー 1 個、RGB LED 1 個を、
基板上の ATmega328P が束ねているユニット。ホストから見える相手は ATmega であって
タッチコントローラではない。**つまり I2C の相手は固定機能 IC ではなくファームウェアであり、
通信仕様はこの製品固有のもの**である。

M5Stack のカタログでは「Unit 16-Key Capacitive Touch」と「Unit Makey」の
**2 つの名前で売られている同一製品**である（`chips/m5stack-mcu-u026.yaml` の notes も
この点に触れている）。ドキュメントの URL は `unit/makey`。

ユニット単体でも楽器として完結している点が特徴で、**ホストが何も指示しなくても、
接点に触れば基板上のブザーが鳴り LED が光る**。I2C はあくまで「今どの接点が触られているか」を
外に出すための口である。

できること:

- 16 接点それぞれの押下状態をビットとして読める。**同時押しが分かる。**
- （公開されている firmware ソースを信じるなら）4 バイト書き込みで LED 色を送る口がある。
  ただし**そのバイトは firmware 内で使われていない**（下記「利用上の注意」）。

できないこと・持っていないもの:

- **レジスタが無い。** ファームウェアのバージョンもハードウェア種別も読めない。
  **I2C から「これは Makey だ」と同定する手段が無い。**
- **アドレスを変更できない。**
- **割り込み線が無い。** ポーリングのみ。
- **押下・離上のイベントが無い。** 返るのは瞬間の状態ビットだけで、エッジはホスト側で作る。
- **接点の生の静電容量値や感度しきい値を読めない・設定できない。**
- **ブザーの音程や鳴らすかどうかを I2C から制御できない。** firmware が接点ごとに固定の
  音階を鳴らす。**黙らせる手段が無い。**
- **接点の押下順序が分からない。** 返るのは同時刻のビット列だけ。

## 早見表

| 項目 | 値 |
|---|---|
| I2C アドレス | `0x51`（固定。変更手段なし）。**ただし公開 firmware ソースは `0x01` を登録している。下記注意** |
| 電源 | 5V（Grove の赤） |
| インタフェース | Grove HY2.0-4P（M5Core の PORT A） |
| I2C 速度 | **不明。** ベンダーのサンプルは `Wire.begin()` を引数無しで呼ぶだけで、ホスト既定（M5Stack Core では 100kHz）に従う |
| 中身 | ATmega328P + タッチ接点 ×16 + ブザー ×1 + RGB LED（NeoPixel）×1 |
| 割り込み | 無し（ポーリング） |
| 転送の形 | **ポインタバイト無し**の連続読み出し。ベンダーのサンプルは 2 バイト、firmware は 3 バイト送る |
| ビットの意味 | `1` が押下。byte0 の bit0 が接点 0 … byte1 の bit7 が接点 15 |
| 寸法 / 重量 | 32.0 × 24.0 × 8.0mm / 7.0g |

## レジスタ / コマンド

**レジスタは無い。ポインタバイトを書かずにいきなり読む。**

ベンダーのホスト側サンプル（`M5Stack` ライブラリの `examples/Unit/MAKEY/MAKEY.ino`）は
`Wire.requestFrom(0x51, 2)` を呼び、返った 2 バイトをビットで判定している。ポインタバイトの
書き込みは無い。

読み出しの中身（公開されている**スレーブ側 firmware ソース**が根拠）:

| バイト | 意味 |
|---|---|
| byte0 | 接点 0〜7。**bit n が接点 n**。`1` = 押下 |
| byte1 | 接点 8〜15。**bit n が接点 8+n**。`1` = 押下 |
| byte2 | **意味が無い。firmware が値を代入していない未初期化変数がそのまま出る**（下記注意） |

firmware の該当行はこうなっている（`Makey328.ino`）。

```
Key1 = key[0]+key[1]*2+key[2]*4+key[3]*8+key[4]*16+key[5]*32+key[6]*64+key[7]*128;
Key2 = key[8]+key[9]*2+key[10]*4+key[11]*8+key[12]*16+key[13]*32+key[14]*64+key[15]*128;
```

**I2C に出るビットは `1` = 押下である。** firmware 内部では AVR のポートを
`(PIND & 0x01) == 0x00` すなわちアクティブ Low で読んでいるが、そこで `key[n] = 1` に
正規化してから上の式でパックしている。**回路図やポートの生ビットから極性を推測すると
逆になる。**

書き込み側は 4 バイト固定の 1 種類だけが実装されている。

```
void receiveEvent(int howMany)
{
  if (howMany != 4) { /* 読み捨てて return */ }
  LedR = Wire.read();
  LedG = Wire.read();
  LedB = Wire.read();
  LedW = Wire.read();
}
```

**ポインタバイトもコマンドバイトも無い。** ちょうど 4 バイト書けば RGBW として受け取られ、
それ以外の長さは黙って捨てられる。ただし後述のとおり、受け取った 4 バイトは
firmware のどこでも使われていない。

**何があればこれが確定するか**（有用な順）:

1. **実機のキャプチャ。** 本ユニットは「公開ソースと実機がどこまで一致するか」を
   確かめる作業そのものが成果になる。特に (a) スレーブアドレスは本当に `0x51` か、
   (b) 3 バイト目に何が出るか、(c) 4 バイト書いたとき LED が変わるか、の 3 点。
2. **実機の ATmega328P からの flash 吸い出し。** 公開ソースが出荷バイナリと違うことは
   ほぼ確実（下記）なので、出荷 firmware そのものが最終的な一次資料になる。
3. **UIFlow が実機を叩くところのキャプチャ。**

## 典型的な使い方

1. Wire を開く（ベンダーのサンプルは引数無しの `Wire.begin()`）。
2. `0x51` に 2 バイト要求する。**ポインタバイトは書かない。**
3. byte0 の bit n が接点 n、byte1 の bit n が接点 8+n。**`1` が押下。**
4. 前回のビット列と比較して押下・離上のエッジをホスト側で作る。デバイス側は状態しか返さない。
5. 3 バイト目は要求しない。要求しても意味が無い。

## 利用上の注意

- **公開されている firmware ソースは、そのままではコンパイルできない。**
  `Makey_NewVersion/firmware_328p/Makey328/Makey328.ino` の `loop()` の中に、
  コメントにもなっていない裸のテキスト（`0x0001 1` … `0x8000` という 16 行の表）が
  貼り込まれたまま残っている。**したがってこのソースは出荷バイナリそのものではない。**
  ビット配置の根拠としては使えるが、細部を仕様として扱ってはいけない。
- **公開ソースのスレーブアドレスは `0x51` ではなく `0x01` である。**
  `Wire.begin(0x1);` と literal で書かれており、`#define` による定義も無い。
  一方、製品ページとホスト側サンプルはどちらも `0x51` と言う。**この食い違いは未解決。**
  実機のアドレスは `0x51` だと考えるのが妥当（ホスト側サンプルが動いている以上）だが、
  **公開ソースからアドレスを読み取ってはいけない。** ビット配置の根拠としてだけ使うこと。
- **3 バイト目（`Key3`）は未初期化のゴミである。** firmware は `int Key1, Key2, Key3;` と
  グローバル宣言したあと `Key3` に一度も代入せず（代入行はコメントアウトされている）、
  `requestEvent()` で `Wire.write(Key3)` している。**3 バイト要求すると意味の無いバイトが返る。**
  ベンダーのホスト側サンプルが 2 バイトしか要求しないのはこのためだと考えられる。
- **LED 書き込みは受け取られるが何もしない。** `receiveEvent()` が代入する
  `LedR/LedG/LedB/LedW` は firmware のどこからも参照されていない。LED の色は
  `RGB(c)` 関数が持つ 18 色の固定テーブルから、**押された接点番号で選ばれる**。
  つまり **I2C から LED 色を指定することはできない**（少なくとも公開ソースの版では）。
  4 バイト書いても副作用が無いだけ、ということになる。
- **離上が約 80ms 引き延ばされる。** firmware は接点ごとに `key_delay[n] = 20` を仕込み、
  離れたあと 20 回のループを数えてから `key[n] = 0` に戻す。ループ末尾に `delay(4)` が
  あるので、**触るのをやめてから約 80ms は「押されている」と報告され続ける**。
  チャタリング除去として意図されたものだが、**ホスト側で短い連打を検出したいときの
  分解能の下限がここで決まる。** ポーリングを速めても改善しない。
- **ブザーを黙らせられない。** 接点に触れると firmware が `tone(A3, ...)` で 20ms 鳴らす。
  I2C からこれを止める口は無い。静かな環境で使いたい場合はハードウェア的に潰すしかない。
- **本カタログ内の `0x51` 衝突**（`0x51` は本カタログで最も混み合うアドレスの一つ）:
  - [`chips/hym8563.yaml`](../../chips/hym8563.yaml) — HYM8563 RTC（M5Stack Unit RTC）。
    **固定アドレス `0x51` で変更不可。本機と同時に使えない。** PCF8563 互換品も同じ。
  - [`chips/eeprom.yaml`](../../chips/eeprom.yaml) — M5Stack Unit AMeter の
    キャリブレーション EEPROM が `0x51`。**Unit AMeter と同時に使えない。**

  いずれも本機側でアドレスを変えられないので、回避手段は I2C マルチプレクサ
  （[`chips/tca9548a.yaml`](../../chips/tca9548a.yaml) / [`chips/pca9548a.yaml`](../../chips/pca9548a.yaml)）を
  挟むか、別のバスに分けるかである。
- **I2C から機種を同定できない。** バージョンレジスタも ID レジスタも無い。`0x51` が
  ACK したという事実だけでは、RTC なのか AMeter なのか Makey なのか分からない。
  **`0x51` に何かが居るときは、まず何を挿したか思い出すこと。**
- **I2C 速度が不明。** ベンダーのサンプルが `Wire.begin()` を引数無しで呼ぶので、
  実際に何 kHz で検証されたのかが分からない。ATmega328P のスレーブ実装は 400kHz でも
  動くことが多いが、**本機で確かめられていない。** 迷うなら 100kHz。
- **本ガイドに書かれたことは、寸法・重量を除いてどれも実測で確認されていない。**
  そのうえ最も詳しい情報源（firmware ソース）が出荷バイナリと一致しない疑いが濃い。

## 出典と確度

- **datasheet: 無い。** M5Stack はこのユニットについて I2C プロトコル文書を公開していない。
  [`chips/m5stack-mcu-u026.yaml`](../../chips/m5stack-mcu-u026.yaml) の `datasheets` は
  製品ページ 1 件のみで `kind: product-page`。製品ページに Protocol の節も無い
  （Joystick や CardKB にはある 1 行表すら無い）。
- **ベンダー Arduino ライブラリ: 無い。** `M5Unit-Makey` に相当するリポジトリは存在せず、
  [`collection/vendor_libraries.toml`](https://github.com/tanakamasayuki/I2CDeviceDB/blob/38f1d82/collection/vendor_libraries.toml) にも
  `collection/vendor/` にもエントリが無い。M5Unified / M5GFX にもこのユニットを扱う
  コードパスは無い（Unit LCD のような一般ライブラリ経由の道は本機には無い）。
- **`profiles/`: 無い。キャプチャ: 無い。**
- アドレス `0x51` と 2 バイト読み: **製品ページの仕様とホスト側サンプル
  `MAKEY.ino` の `Wire.requestFrom(0x51, 2)` に基づく**（この 2 つは一致している）。
- **ビット配置（byte0 = 接点 0〜7、byte1 = 接点 8〜15、`1` = 押下）、3 バイト送信、
  `Key3` が未初期化であること、4 バイトの RGBW 書き込みが受理だけされて使われないこと、
  離上の約 80ms 引き延ばし**: すべて**ベンダー公開の firmware ソース `Makey328.ino` から
  起こした推定**。実測では未確認であり、しかもそのソースはコンパイルが通らない状態で
  公開されているため、**出荷バイナリと同一である保証は無い。**
- **矛盾として記録しておくべき点**: 公開 firmware ソースは `Wire.begin(0x1)`、
  製品ページとホスト側サンプルは `0x51`。**未解決。**
- **次にやるべき最も有用な一手**: `0x51` に対する read-only の probe で、
  **要求長 1〜4 バイトの応答を接点を触りながら記録すること。** 1 回のキャプチャで
  「ビットが `1` = 押下か」「3 バイト目にゴミが出るか」「離上が 80ms 遅れるか」の
  3 つが同時に確定し、本ガイドで最も疑わしい部分（公開ソース由来の記述）が
  そのまま裏取りできる。アドレスが `0x51` であることの確認も同時に済む。
