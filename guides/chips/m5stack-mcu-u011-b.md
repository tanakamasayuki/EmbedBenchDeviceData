# Unit EXT.IO2 (U011-B) — 8 チャンネル IO 拡張ユニット

> I2C 1 本で 8 本の IO を生やすユニット。ピンごとに「デジタル入力 / デジタル出力 / ADC /
> サーボ / RGB LED」のいずれかのモードを割り当てて使う。
>
> **確度**: M5Stack が `M5Unit-EXTIO2` リポジトリに Protocol PDF（FW V1 と V3）を置いており、
> レジスタ表はそこと `M5Unit-EXTIO2` ライブラリのソースの両方にある。本文の転送長・
> バイト順・アクセス方向は**ライブラリ実装と PDF から起こした推定**で、実測では未確認。
> 手元の個体の firmware がどちらの版かは `0xFE` を読むまで分からない。

## これは何か

STM32F030F4P6 に M5Stack のファームウェアを載せ、2.54mm ピッチのピンヘッダ 8 本を
I2C から叩けるようにしたユニット。ホストから見える相手は STM32 であって、IO ポート
そのものではない。**つまりレジスタマップはこの製品固有のもの**で、汎用 IO エキスパンダ
（PCA9554 など）とは互換性が無い。

8 本のピンはそれぞれ独立に、次の 5 モードのどれかに設定して使う。

| モード値 | 動作 |
|---|---|
| 0 | デジタル入力 |
| 1 | デジタル出力 |
| 2 | ADC 入力 |
| 3 | サーボ制御 |
| 4 | RGB LED（NeoPixel）制御 |

できること:

- ピン単位でのデジタル入出力。入出力レベルは 3.3V。
- ADC 読み出し。8bit（0〜255）と 12bit（0〜4095）の 2 通りの読み方がある。
- サーボ制御。角度（0〜180 度）でも、パルス幅（500〜2500 マイクロ秒）でも指定できる。
- RGB LED の色指定（R/G/B 各 0〜255）。
- I2C アドレスの変更（1〜127、既定 `0x45`）。
- ファームウェアバージョンの読み出し。

できないこと・持っていないもの:

- **割り込み線は無い。** 入力の変化を知るにはポーリングするしかない。
- **PWM 出力は FW V1 には無い。** V3 で追加された機能で、`M5Unit-EXTIO2` v1.0.3 の
  ライブラリ側も PWM を実装していない。手元の個体で使えるかどうかは firmware 次第。
- **ADC の電圧換算に必要な情報が公開されていない。** 返るのは 0〜4095 のカウント値だけで、
  基準電圧も入力レンジも Protocol PDF・製品ページのどちらにも書かれていない。**単位は無い。**
- **サーボはハードウェア PWM ではない。** Protocol PDF の注記により、MCU が
  ソフトウェアで IO をトグルして生成している。
- **RGB LED は 1 ピンあたり 1 色分（3 バイト）しか領域が無い。** ストリップ長の設定や
  複数 LED の一括塗りつぶしは無い（PbHub にはある）。1 ピンに何個まで繋がるかは未記載。
- **出力の駆動能力（1 ピンあたりの電流、合計電流）はどこにも書かれていない。**
- モード・出力値・アドレスは Protocol PDF 上は読み戻せる（W/R）ことになっているが、
  ライブラリはいずれも読まないので、実際に読めるかは未確認。

## 早見表

| 項目 | 値 |
|---|---|

| アドレス変更 | レジスタ `0xFF` に 1〜127 を書き込み。**書いた直後から新アドレスで応答する** |
| 電源 | 5V（Grove の赤）。IO の入出力レベルは 3.3V |
| インタフェース | Grove HY2.0-4P + 2.54mm ピンヘッダ 8 本 |

| 割り込み | 無し（ポーリング） |
| バイト順 | 12bit ADC とサーボパルスはリトルエンディアン（LSB first）。RGB は R, G, B の順 |

## レジスタ

すべての機能ブロックが「ベースアドレス + ピン番号 × 要素幅」のバンクになっている。
要素幅がブロックごとに違うので、ピン n のアドレスはブロックごとに計算が変わる。

| ベース | 要素幅 | 範囲 | R/W | 意味 |
|---|---|---|---|---|
| `0x00` | 1 | `0x00`–`0x07` | W（PDF は W/R） | ピンモード。値 0〜4（上表） |
| `0x10` | 1 | `0x10`–`0x17` | W | デジタル出力レベル。0=LOW, 1=HIGH |
| `0x18` | 1 | `0x18` | W | 8 本まとめてビットマップ（bit n = ピン n）。**ベンダー PDF に記載が無い** |
| `0x20` | 1 | `0x20`–`0x27` | R | デジタル入力レベル。0=LOW, 1=HIGH |
| `0x28` | 1 | `0x28` | R | 8 本まとめてビットマップ。**ベンダー PDF に記載が無い** |
| `0x30` | 1 | `0x30`–`0x37` | R | 8bit ADC。0〜255。単位なし |
| `0x40` | 2 | `0x40`–`0x4F` | R | 12bit ADC。0〜4095、**LSB first**。単位なし |
| `0x50` | 1 | `0x50`–`0x57` | W（PDF は W/R） | サーボ角度。**0〜180 度** |
| `0x60` | 2 | `0x60`–`0x6F` | W（PDF は W/R） | サーボパルス幅。**500〜2500 マイクロ秒**、LSB first |
| `0x70` | 3 | `0x70`–`0x87` | W（PDF は W/R） | RGB LED。**R, G, B の順**（数値ではないのでエンディアンの話ではない） |
| `0xFE` | 1 | — | R | ファームウェアバージョン |
| `0xFF` | 1 | — | W（PDF は W/R） | I2C アドレス。1〜127 |

ピン n のアドレス:

- モード / デジタル出力 / デジタル入力 / 8bit ADC / サーボ角度 → `ベース + n`
- 12bit ADC / サーボパルス → `ベース + n*2`
- RGB → `0x70 + n*3`（ピン 5 の途中から `0x80` の行にまたがる）

**転送の形**: 書き込みは「ポインタバイト + ペイロード」を 1 トランザクションで送る。
読み出しはポインタバイトを書いて **STOP を打ってから**（`endTransmission()` の既定）
改めて読み出しトランザクションを起こす。Unit Scroll のような repeated START ではない。

## 典型的な使い方

1. `0xFE` を読んでファームウェアバージョンを確認する。通信が成立しているかの確認も兼ねる。
2. 使うピンのモードを `0x00 + n` に書く。**ここを飛ばすと以降の操作は効かない。**
   ライブラリの `begin()` はモードを一切設定しない。
3. 8 本すべてを同じモードにするなら `0x00` に 8 バイトまとめて書ける。
4. あとはモードに応じたバンクを読み書きする。
   - デジタル入力 → `0x20 + n` を 1 バイト読む
   - 12bit ADC → `0x40 + n*2` から**必ず 2 バイト**読む
   - サーボ → `0x50 + n` に角度、または `0x60 + n*2` に**必ず 2 バイト**でパルス幅
   - RGB → `0x70 + n*3` に**必ず 3 バイト**で R, G, B

## 利用上の注意

- **モードを設定するまで何も動かない。** `begin()` はモードを触らないので、
  デジタル出力を書いても、ADC を読んでも、モードが合っていなければ意味のある結果にならない。
  最初に踏む落とし穴はほぼこれ。
- **12bit ADC は「2 バイト境界から、ちょうど 2 バイト」でしか読めない。**
  Protocol PDF が明示的に書いている制約で、`0x40` から 1 バイト、`0x41` から 2 バイト、
  `0x48` から 4 バイトは**いずれも誤りとして例示されている**。同じ制約がサーボパルス
  （`0x60` から 2 バイト境界・2 バイト固定）と RGB（`0x70` から 3 バイト境界・3 バイト固定）
  にもある。まとめ読みで 8ch 分を一括取得する、という使い方はできない。
- **バイト順が一様でない。** 12bit ADC とサーボパルスはリトルエンディアン（下位バイトが先）。
  一方 RGB は R → G → B の順で、これは数値ではなく色チャンネルの並びなので
  「ビッグエンディアン」と考えると混乱する。ライブラリは `0xRRGGBB` の uint32 を
  上位バイトから順に出しているだけである。
- **`0x18` と `0x28`（8 本一括のビットマップ）はベンダーの Protocol PDF に載っていない。**
  ライブラリの `setAllDigitalOutputs()` / `getAllDigitalInputs()` はこのアドレスを叩くが、
  PDF の表では `0x10` 行・`0x20` 行とも列 0〜7 しか埋まっていない。firmware の
  未公開機能なのか、ライブラリ側の思い込みなのかは**未確認**。
- **ライブラリのピン番号チェックが不揃い。** `setLEDColor()` と `setPinMode()` は
  `pin > 7` を弾くが、`setDigitalOutput()` / `setServoAngle()` / `setServoPulse()` は
  弾かない。`setDigitalOutput(8, ...)` は `0x10 + 8` = `0x18`、つまり**一括ビットマップの
  アドレスに書き込む**。8 本目のつもりで 8 を渡すと全ピンが書き換わる。
- **サーボはソフトウェア生成なので、I2C を叩きすぎると震える。** Protocol PDF の注記
  そのもの。ADC を高頻度でポーリングしながらサーボを動かす構成は避ける。
- **アドレス変更は即時反映。** `0xFF` に書いた次のトランザクションはもう新アドレス宛に
  出さないと応答しない。書き換えた値を忘れると `0x45` を探しても見つからない個体が残る。
  復旧は scan で全アドレスを舐めるしかない。有効値は 1〜127。
- **ライブラリの `setAllPinMode()` には到達不能コードがある。** `return writeBytes(...)` の
  後ろにピンごとのフォールバックループが書かれているが、実行されない。バス上に出るのは
  `0x00` への 8 バイトブロック書き込み 1 回だけである。デバイスの仕様ではなくライブラリの都合。
- **ライブラリの `getDigitalInput()` は失敗と LOW を区別できない。** 読み出しに失敗しても
  `0` を返すので、通信エラーが「ピンが LOW」に化ける。`getAnalogInput()` も同じで、
  失敗時は `0` を返す。
- **ADC の値を電圧として扱ってはいけない。** 0〜4095 のカウントに対する換算係数が
  公開されていない。基準電圧を知りたければ実測するしかない。
- **PWM を期待して買わない。** ピンモード 5（PWM）とレジスタ `0x90` / `0xA0` は FW V3 で
  追加されたもので、V1 の firmware には存在しない。ライブラリ v1.0.3 も未対応。

## 出典と確度

- レジスタのアドレスと意味: `M5Unit-EXTIO2` v1.0.3 のソース（`src/M5_EXTIO2.h` の `#define` 群と
  `src/M5_EXTIO2.cpp` のアクセサ本体）。M5Stack の Protocol PDF（V1 / V3）とも突き合わせた。
- 値域（ADC 0〜4095、サーボ 0〜180 度 / 500〜2500us、RGB 0〜255、アドレス 1〜127）、
  アライメント制約、サーボがソフトウェア生成であること: **Protocol PDF 由来**。
- 転送長・アクセス方向・バイト順: ライブラリのメソッド本体から起こした**推定**。
- **未確認**: 実機のキャプチャがまだ無い。手元の個体の firmware 版（V1 か V3 か）、
  `0x18` / `0x28` の実在、モード・出力・アドレスの読み戻し、400kHz での動作は
  いずれも確かめられていない。
- **未調査**: 書き込み側の挙動全般。`scenarios/m5stack-mcu-u011-b/p0.yaml` は
  `safety: read-only` で、モード設定・デジタル出力・サーボ・RGB・アドレス変更は
  すべて `deferred` に置かれている。
- ADC の基準電圧・入力レンジ、IO の駆動能力は**一次資料に記載が無い**。
