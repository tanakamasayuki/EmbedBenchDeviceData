# Unit LCD (U120) — I2C 接続の 1.14 インチカラー液晶ユニット

> 135 × 240 のカラー液晶を **I2C 1 本で描画する**ユニット。ホストから見えるのは液晶ドライバ
> （ST7789V2）ではなく、その手前に立っている ESP32-PICO のファームウェアである。
> **レジスタマップではなく「コマンドストリーム」を喋る**点が、本カタログの他ユニットと決定的に違う。
>
> **確度**: 6 機種の中で本機だけは**ベンダーが完全なコマンド表を製品ページに公開している**。
> さらに M5GFX（LovyanGFX 由来）に完全な実装があり、両者は整合している。
> `profiles/m5stack-mcu-u120.yaml` が無いのは資料が無いからではなく、
> **プロトコルがレジスタファイルではないため `transport: i2c-register` で表現できないから**である。
> それでも**バス上で確認された挙動は一つも無く、`observations/` にキャプチャは無い。**

## これは何か

1.14 インチ・135 × 240 ドット・RGB666（262,144 色）の TFT 液晶と、それを駆動する
ST7789V2 を、ESP32-PICO に載った M5Stack ファームウェアが束ねているユニット。
**ST7789V2 は ESP32 の SPI にぶら下がっていて、外部の I2C バスには出てこない。**
ホストが I2C で送るのは「この矩形をこの色で塗れ」「このピクセル列を書け」といった
**描画コマンド**であり、ST7789 のレジスタではない。

言い換えると、これは「I2C につながる液晶ドライバ」ではなく
**「I2C プロトコルを喋る小さなグラフィックスコプロセッサ」**である。

できること:

- 矩形塗り、ドット描画、矩形コピー、画像転送（RGB332 / RGB565 / RGB888 / ARGB8888 の 4 形式）。
- **RLE 圧縮での画像転送。** I2C の帯域が細いことへの対策として firmware 側に用意されている。
- **アルファブレンド。** ARGB8888 での矩形塗りと、アルファチャネルだけを送る転送形式がある。
- **VRAM の読み戻し。** 描いた内容をピクセル単位で読み返せる。
- バックライト輝度、色反転、回転（0〜7、上下反転を含む）、スリープ、省電力モード。
- **ファームウェアの ID とバージョンを読める。**（`READ_ID` が `0x77 0x89 …` を返す）
  **本カタログの firmware 定義ユニットの中で、I2C から確実に機種同定できる数少ない一台。**
- **コマンドバッファの空きを読める。** ホスト側でフロー制御ができる。
- I2C アドレスを変更できる。
- I2C 経由でファームウェアを更新できる。

できないこと・持っていないもの:

- **タッチパネルが無い。** 出力専用。
- **フォントもテキスト描画コマンドも無い。** 文字はホスト側（M5GFX）がラスタライズして
  ピクセルとして送る。
- **割り込み線が無い。** 描画完了通知は無く、`READ_BUFCOUNT` をポーリングする。
- **部分更新の通知・ティアリング同期が無い。** VSync に相当するものは公開されていない。
- **座標が 1 バイトずつ。** 135 × 240 なので収まっているが、パラメータの幅に余裕は無い。

## コマンド

**レジスタは無い。** アドレス `0x3E` への書き込みトランザクションに、コマンドバイトと
そのパラメータを詰めて送る。ポインタバイトという概念が無く、代わりに
**「1 バイト目がコマンド、以降がそのコマンド固有のパラメータ」**という形式である。

### 転送の規則（ここが一番の勘所）

製品ページが明記している 3 つの規則:

- **コマンドの途中で I2C の STOP や RESTART が入ると、そのコマンドは処理されない。**
  最後まで 1 回の転送で送り切る必要がある。
- **固定長コマンドのあとには、続けて次のコマンドを送ってよい。** 1 トランザクションに
  何個でも詰められる。
- **可変長コマンドのあとは I2C 通信を停止（STOP）してコマンドの終わりを示す。**
  可変長コマンドは STOP まで延々とピクセルを食い続けるので、STOP が終端記号になる。

### 読み出しコマンド

| コマンド | 名前 | 応答 |
|---|---|---|
| `0x04` | READ_ID | 4 バイト。`[0]` `0x77` `[1]` `0x89` `[2]` メジャー版数 `[3]` マイナー版数 |
| `0x09` | READ_BUFCOUNT | 1 バイト。受信可能なコマンド数（0〜255）。**小さいほど余裕が無い。** 繰り返し読める |
| `0x81` | READ_RAW_8 | RGB332 を STOP まで連続 |
| `0x82` | READ_RAW_16 | RGB565 を STOP まで連続 |
| `0x83` | READ_RAW_24 | RGB888 を STOP まで連続 |

**単位とバイト順**: 座標はすべて**ピクセル単位の 1 バイト**（X は 0〜134、Y は 0〜239。
回転すると入れ替わる）。色は形式ごとのバイト数をそのまま並べる。輝度は 0〜255。
既定ではバイトスワップ無し（`0x3A` で切り替えられる）。

**転送の形**: 書き込みは「コマンドバイト + パラメータ」を 1 トランザクションで送る。
読み出しは M5GFX の実装ではコマンドを書いたあと**同一トランザクション内で読みに入る**
（`writeCommand()` → `readBytes()`）。

## 典型的な使い方

1. コマンド `0x04` を送って 4 バイト読む。**先頭 2 バイトが `0x77 0x89` であることを確認する。**
   これが本ユニットであることの確認であり、M5GFX の `Panel_M5UnitLCD::init()` も
   まったく同じことをしている。一致しなければ初期化を失敗させる。
2. 必要なら `0x36`（回転）、`0x22`（輝度）、`0x38`（電力モード）を設定する。
3. 塗るだけなら `0x69`〜`0x6C`（色付き矩形塗り）を投げる。1 トランザクションに
   複数の矩形を詰められる。
4. 画像を出すなら `0x2A` / `0x2B` で範囲を決めてから `0x42`（RGB565）などで
   ピクセルを流し、**最後に STOP を打って終端する。**
5. 大きな画像や単色領域が多い画像は RLE 版（`0x4A` など）を使う。I2C は 400kHz が上限で、
   135 × 240 の RGB565 全画面は 64,800 バイト＝**400kHz でも 1.3 秒以上**かかる。
   全画面を毎フレーム描き替える使い方は成立しない。
6. 連続して大量に投げる場合は `0x09` で空きを見ながら流す。

## 利用上の注意

- **コマンドの途中で STOP や RESTART を入れてはいけない。** これが本機で最大の落とし穴。
  他のデバイスを同じバスに混ぜて**トランザクションを割り込ませると、描画コマンドが
  途中で捨てられて表示が壊れる。** M5GFX が Unit LCD のパネル設定で
  `cfg.bus_shared = false` にしているのはこのためである。
  I2C マルチプレクサ（[`chips/tca9548a.yaml`](../../chips/tca9548a.yaml)）を挟む場合も、
  **チャネル切り替えのトランザクションが描画の途中に入らないように**組む必要がある。
- **可変長コマンドは STOP でしか終わらない。** `0x42` などを送ったあとに続けて別のコマンドを
  同じトランザクションで送ると、**そのコマンドバイトはピクセルデータとして解釈される。**
  可変長のあとは必ず STOP。
- **バッファ溢れは静かに壊れる。** ESP32 側のコマンドバッファが尽きた状態で送り続けると
  どうなるかは公開されていない。M5GFX は `_check_repeat()` の中で `READ_BUFCOUNT` を読み、
  残量が閾値を下回るとトランザクションを切って読み直す、という制御を入れている。
  **自前でプロトコルを組む場合、このフロー制御を省くと不定の症状（表示の欠け、
  コマンドの取りこぼし）が出る。**
- **アドレス変更は復旧が面倒。** `0xA0` は新アドレスとそのビット反転値の両方を要求する
  （誤書き込み防止）が、いったん変えると `0x3E` を探しても見つからない。
  M5GFX 側も `M5UNITLCD_ADDR`（既定 `0x3E`）をコンパイル時定数として持つので、
  **ライブラリのマクロも一緒に直さないとつながらない。** 復旧はバススキャンで探す。
- **`0xFF`（RESET）と `0xF0`〜`0xF2`（ファーム更新）は製品ページのコマンド表に載っていない。**
  M5GFX のヘッダにのみ定義がある。**通常のアプリケーションから触る理由は無い。**
  4 バイトのマジック（`0x77 0x89`）で守られているので誤爆はしにくいが、
  ファーム更新コマンドを誤って完走させると表示できない個体が残る。
- **`READ_ID` の 3・4 バイト目の解釈が資料で食い違う。** 製品ページの表は
  `[2]` Major / `[3]` Minor と書き、M5GFX のヘッダのコメントは
  「`0x77 0x89 0x00 0x??`（最後の 1 バイトはファームウェアバージョン）」と書く。
  **同定に使ってよいのは先頭 2 バイトだけ**と考えるのが安全で、M5GFX の実装も
  `buf[0] == 0x77 && buf[1] == 0x89` しか見ていない。
- **読み出しのクロックがライブラリ側で丸められる。** `M5UnitLCD.h` は
  `freq_read = freq > 400000 ? 400000 + ((freq - 400000) >> 1) : freq` として、
  400kHz を超える指定に対して読み出しだけ控えめな値を使う。
  **400kHz 超で使うと書きと読みでクロックが変わる**ことを知らないと、キャプチャを見て混乱する。
  なお製品ページは 400kHz を上限と明記しているので、超える設定はそもそも仕様外である。
- **`0x45` / `0x4D`（アルファのみの転送）は「最後に設定した描画色」に依存する。**
  ステートを持つコマンドなので、送る順序を変えると結果が変わる。
- **I2C は帯域が足りない。** 上に書いたとおり全画面 RGB565 で 1.3 秒以上かかる。
  UI を作るなら差分だけを描く、RLE を使う、RGB332 に落とす、のいずれかが要る。
  **「小さな液晶が I2C 1 本で足せる」ことが価値であって、動画が出せるわけではない。**
- **本カタログ内の `0x3E` 衝突: 現時点で無い。** `0x3E` を使う chip は本機だけである。
  ただし**近傍は表示デバイスで混み合っている**ので、`0xA0` でアドレスを動かすときは
  避けること: [`chips/m5stack-mcu-u158.yaml`](../../chips/m5stack-mcu-u158.yaml)（Unit Glass）が `0x3d`、
  [`chips/sh1107.yaml`](../../chips/sh1107.yaml) / [`chips/ssd1309.yaml`](../../chips/ssd1309.yaml) /
  [`chips/ssd1315.yaml`](../../chips/ssd1315.yaml) がいずれも `0x3c` / `0x3d`。
- **`profiles/` が無いのは資料不足ではない。** 本機のプロトコルはコマンドストリームであり、
  「アドレス・長さ・R/W」の三つ組で表現するレジスタモデルに乗らない。
  無理に `transport: i2c-register` で書くと、可変長コマンドと STOP 終端という
  本質的な部分が落ちる。**このガイドが本機に関する本リポジトリ側の主たる記述である。**
- **本ガイドに書かれたことは、寸法・重量・電流を除いてどれも実測で確認されていない。**
  コマンド表そのものはベンダー公式なので確度は高いが、実機がそのとおり応答するかは未検証。

  **代わりに汎用ライブラリ M5GFX（LovyanGFX 由来）が完全な実装を持っている**
  （`src/M5UnitLCD.h` と `src/lgfx/v1/panel/Panel_M5UnitLCD.{hpp,cpp}`、
  ユーザ向けの入口は `#include <M5UnitLCD.h>` と `class M5UnitLCD : public M5GFX`）。
  M5GFX は Arduino Library Manager 経由のライブラリなので、
  本リポジトリの `collection/vendor/` には現れず、スケッチ側でバージョン指定して取得される。
  **「ライブラリを探すならここ」という一点だけでも、本ガイドで最も実用的な情報である。**
- `0x3A`（SET_BYTESWAP）、`0xF0`〜`0xF2`（ファーム更新）、`0xFF`（RESET）、
  リセット後の 300ms 待ち、`READ_BUFCOUNT` によるフロー制御の具体的な手順:
  **M5GFX のソースから起こした推定。製品ページのコマンド表には載っていない。**
- `READ_ID` の応答先頭 2 バイトが `0x77 0x89` であること: 製品ページと M5GFX の
  `init()` の両方に現れ、一致している。
- **`profiles/`: 無い。** 資料不足ではなく、レジスタモデルで表現できないため
  （上記「利用上の注意」参照）。
- **キャプチャ: 無い。** `observations/` にも `scenarios/` にもこのチップのディレクトリは無い。
  実機がコマンド表どおりに応答するか、バッファが尽きたときにどう振る舞うかは未確認。
- **次にやるべき最も有用な一手**: **M5GFX が実機を描画するところをキャプチャすること。**
  ライブラリが手元にあり（`#include <M5UnitLCD.h>` の数行で動く）、コマンド表も
  ベンダー公式で揃っているので、**「表と実際のバイト列を突き合わせる」という
  本リポジトリが最も得意な作業がそのまま成立する数少ないユニット**である。
  特に価値が高いのは、可変長コマンドの STOP 終端と `READ_BUFCOUNT` によるフロー制御の
  実際の様子で、これはコマンド表を読んだだけでは分からない。
